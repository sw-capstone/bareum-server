# 엔티티 설계 및 구현 규칙

## 1. 패키지 구성

- 공통 코드는 `global`, 기능별 코드는 `domain.<도메인>`에 둔다.
- 엔티티는 `entity`, 상태·종류 Enum은 같은 수준의 `enums`에 둔다.
- 도메인 에러 코드와 예외는 해당 도메인의 `exception`에 둔다.
- 클래스와 패키지는 실제 필요할 때 생성한다.

**근거:** 관련 코드를 도메인별로 모으고, 여러 계층에서 사용하는 Enum을 엔티티 내부에 종속시키지 않는다.

## 2. 식별자와 필드

- BIGINT PK는 `Long` + `GenerationType.IDENTITY`를 사용한다. UUID 식별자는 UUID를 유지한다.
- 테이블·컬럼 이름, 길이, NULL 허용 여부, 기본값, 정밀도는 ERD에 맞춘다.
- 소수점 점수는 `BigDecimal`, NULL 가능한 숫자·불리언은 래퍼 타입으로 표현한다.
- 상태·종류 Enum은 `EnumType.STRING`으로 저장한다. Enum 상수 이름 변경 시 기존 데이터도 확인한다.

**근거:** 코드와 DB의 의미를 일치시키고, 소수점 오차와 Enum 순서 변경에 따른 데이터 해석 오류를 방지한다.

## 3. 객체 생성

- 엔티티의 외부 생성은 목적이 드러나는 정적 팩터리 메서드로 통일한다.
- 일반 생성자는 `private`, JPA용 기본 생성자는 `protected`로 제한한다.
- Builder는 값 조립이 복잡할 때 내부에서 사용하며, 사용한다면 `private`으로 제한한다.
- 생성 과정에서 필수 조건을 검증하고 초기 상태를 설정한다. 자동 생성 ID·Auditing 시각·고정된 초기 상태는 외부 입력으로 받지 않는다.
- 생성 과정에서 DB 조회나 외부 API 호출을 수행하지 않는다.

**근거:** 생성 목적에 필요한 입력만 받아 잘못된 값 조합과 초기화 누락을 줄인다. JPA의 기본 생성자 요구를 충족하면서 외부의 빈 객체 생성을 제한한다. 내부 Builder까지 일괄 강제하지는 않는다.

## 4. 조회와 변경

- 공개 Setter와 엔티티의 `@Data` 사용을 금지한다.
- 변경은 `changeTitle()`, `markProcessed()`처럼 목적이 명확한 메서드로 수행하고 허용 조건을 검증한다.
- 엔티티 자체의 조건은 엔티티에서, 여러 엔티티의 조회·저장과 트랜잭션은 서비스에서 관리한다.
- 엔티티를 API에 직접 반환하지 않고 DTO로 변환한다. DTO 변환은 단일 객체에 `from()`, 여러 값의 조합에 `of()`를 사용한다.
- 연관 엔티티 전체를 포함하는 `toString`, `equals`, `hashCode`를 일괄 자동 생성하지 않는다.

**근거:** 변경 규칙을 한곳에서 관리하고, DB 구조와 API 응답을 분리한다. 불필요한 연관 객체 탐색과 순환 호출을 줄인다.

## 5. 연관관계

- 단방향을 기본으로 하고, 사용 방식에 따라 양방향·ID 참조를 선택한다.
- 객체 연관관계는 `LAZY`로 설정한다. 필요한 조회 범위는 쿼리에서 결정한다.
- FK의 NULL 허용 여부와 `optional`·`nullable` 설정을 일치시킨다.
- 양방향 관계는 FK를 가진 쪽을 주인으로 정하고 양쪽 객체 참조를 함께 관리한다.
- ID 참조를 사용해도 DB의 FK를 유지한다. 중간 엔티티가 있는 관계를 단순 `@ManyToMany`로 축약하지 않는다.
- cascade는 필요한 작업만 지정한다. 저장 전파가 필요하다는 이유로 삭제까지 전파하지 않는다.
- `REMOVE`·`orphanRemoval`은 소유·삭제 정책이 명확한 경우에만 사용한다. JPA cascade와 DB의 삭제 정책은 별도로 관리한다.

**근거:** 불필요한 양방향 연결과 자동 조회를 줄이고, 객체의 생명주기에 맞춰 저장·삭제 범위를 통제한다.

## 6. JSONB

- JSONB 컬럼은 우선 `JsonNode`로 매핑하고, DB 타입과 JSON 변환 설정을 함께 지정한다.
- 상세 구조는 파서·AI 계약에 맞춰 구체화한다. 이미 정한 NULL 허용 여부와 배열 등의 조건은 유지한다.
- 보호가 필요한 JSON은 내부의 변경 가능한 객체를 그대로 노출하지 않고, 변경 메서드를 통해 수정한다.
- FROZEN 본문과 편집 본문이 같은 변경 가능한 JSON 객체를 공유하지 않도록 복사한다.

**근거:** 미정인 JSON 구조를 성급하게 고정하지 않으면서, 외부의 직접 수정으로 본문 보호 규칙이 우회되는 것을 방지한다.

## 7. 시간 필드

- 시간은 `Instant`로 표현하고 생성·수정 시각은 JPA Auditing으로 기록한다.
- 생성·수정 시각이 모두 있는 엔티티는 `BaseTimeEntity`를 활용한다. 생성 시각은 변경하지 않는다.
- 공통 클래스 상속을 위해 ERD에 없는 시간 컬럼을 추가하지 않는다.
- 분석 시작·종료, 동의 시각 등 업무 시각은 생성·수정 시각과 별도로 관리한다.

**근거:** 기록 방식을 통일하면서 데이터 생성 시점과 실제 업무가 발생한 시점을 구분한다.

## 8. 제약조건과 검증

- PK·FK·NOT NULL·UNIQUE 등 확정된 제약조건을 실제 DB에 반영한다.
- 보고서별 현재 본문 최대 1개, 본문별 성공 분석 최대 1개는 조건부 UNIQUE 인덱스로 보장한다.
- JPA 매핑만으로 표현되지 않는 제약조건은 별도 DDL로 관리하고, `ddl-auto: update`만으로 적용 여부를 판단하지 않는다.
- 업무 조건은 애플리케이션에서 검증하고, 동시 요청에도 유지되어야 하는 유일성은 DB에서도 보장한다.
- 저장·재조회와 제약조건 검증은 PostgreSQL에서 수행한다.

**근거:** 애플리케이션의 사전 검사만으로 막기 어려운 중복과 잘못된 참조를 DB에서도 차단한다.
