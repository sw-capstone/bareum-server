# Flyway 마이그레이션 작성 규칙

## 1. 파일과 버전

- SQL은 `src/main/resources/db/migration/`에 둔다.
- 파일명은 `VYYYY.MM.DD.HH.MM__설명.sql`로 작성하고, 시각은 KST로 통일한다.
- 변경 목적을 알 수 있도록 설명은 `add_report_description`처럼 동사로 시작하는 snake_case를 사용한다.
- 버전은 중복하지 않는다. 신규 파일은 병합 시 기준 브랜치와 적용 대상 DB의 최신 버전보다 높은지 확인한다.

## 2. 변경 단위

- 최초 SQL에는 확정된 테이블과 모든 제약조건·인덱스를 함께 담는다.
- 이후에는 하나의 기능에 필요한 관련 변경을 한 파일로 묶는다.
- 엔티티와 DB 변경을 함께 검토할 수 있도록, 대응하는 SQL을 같은 PR에 포함한다.
- 테스트용 데이터는 운영 마이그레이션에 포함하지 않는다.

## 3. 적용 이력

- 환경마다 DB 구조가 달라지는 것을 막기 위해, 공유 환경에 적용한 파일은 수정·삭제하거나 버전을 바꾸지 않는다.
- 적용된 구조를 수정하려면 새 버전의 SQL을 추가한다.
- 컬럼 삭제·제약조건 강화는 기존 데이터와 실행 중인 코드의 호환성을 확인하고 필요하면 단계별로 나눈다.

## 4. 검증

- 배포 전에 버전 충돌을 발견할 수 있도록, 로컬과 CI에서 테스트 실행 전에 버전 중복을 검사하도록 구성한다.
- PostgreSQL에서 마이그레이션 적용과 JPA 매핑 검증을 확인한다.
- DB 구조 변경은 Flyway가 담당하고, Hibernate는 `ddl-auto: validate`를 사용한다.
