# DEC-DOC-001 보고서 공통 본문 구성과 PDF 파싱 연동

- 상태: 구현 기록 
- 기록일: 2026-10-21
- 관련 작업: 서버 #51, #52, #53 / AI #27, PR #28
- 문서 성격: #51에서 고민한 내용과 구현 방식을 선택한 이유를 정리한 기록

## 1. 이번 작업의 범위를 어디까지 잡을 것인가

직접 입력과 PDF를 같은 구조로 처리할 기반이 필요했지만, 리치 텍스트 에디터와 보고서 접수 서비스까지 함께 구현하면 #51의 범위가 커졌다.

이번에는 공통 본문 모델과 검증, 본문 조립, PDF 파싱 결과 변환, AI 파싱 API 호출과 계약 검증까지 구현했다.

직접 입력은 문단과 표 구조를 공통 처리에 전달할 수 있는 내부 입력 모델만 준비했다. 빈 줄로 문단을 나누는 방식이나 특정 에디터의 JSON 형식을 외부 입력 계약으로 확정하지 않았다.

- #52: 리치 텍스트 에디터와 구체적인 입력 계약
- #53: 접수 API, S3 연결, 파싱 시도와 상태 관리, DB 저장 서비스 연결

에디터가 정해지면 해당 입력을 `BodyInput`으로 변환하는 부분을 추가하는 방향으로 확장한다.

## 2. 파서 결과와 서비스 본문을 같은 모델로 사용할 것인가

PDF 파서 응답을 그대로 서비스 본문으로 사용하면 파서의 형식 변경이 편집, 저장, 분석 입력에 직접 영향을 준다. 직접 입력도 같은 방식으로 처리하기 어렵다.

따라서 PDF 추출 결과와 서비스 공통 본문을 별도 모델과 버전으로 관리했다.

- PDF 추출 결과: 스키마 1.2.0
- 서비스 공통 본문: 스키마 1.0.0
- PDF 파싱 API 요청과 응답: 계약 1.0.0

공통 본문에는 블록, 표, 셀, 섹션, 텍스트 단위와 출처를 담았다. 서비스에서 UUID를 부여하되 파서의 블록 ID와 셀의 행·열 번호는 출처 정보로 보존한다.

셀 출처에는 `parserRow`, `parserColumn`을 필수로 두었다. 서비스 셀 ID만으로는 파서 응답의 어느 셀에서 나온 내용인지 확인할 수 없기 때문이다.

본문 생성 흐름은 다음과 같다.

```text
PDF 파서 응답 → PdfBodyConverter → BodyInput
                                      ↓
                                BodyAssembler
                                      ↓
                             ValidatedReportBody
```

직접 입력도 `BodyInput`을 통해 같은 조립 과정을 사용한다.

## 3. 문장 분리를 정규식으로 계속 관리할 것인가

보고서에는 날짜, 약어, 목록, 인용문, 문장부호가 없는 짧은 표현이 섞여 있다. 정규식만으로 처리하면 새로운 표현이 나올 때마다 예외 규칙을 직접 추가해야 하므로, 문장 분리 라이브러리 도입을 검토했다.

기존 정규식 구현, KiwiJava, OpenNLP를 기존 테스트 샘플과 실제 보고서에서 추출한 텍스트로 비교했다.

| 비교 대상 | 기존 구현 | KiwiJava | OpenNLP |
|---|---:|---:|---:|
| 기존 테스트 15개 | 15개 일치 | 14개 일치 | 11개 일치 |
| 보고서에서 선정한 40개 | 39개 일치 | 40개 일치 | 35개 일치 |

여기서 일치는 사전에 정한 분리 결과와 같다는 의미다. 보고서 40개 사례는 하나의 단위로 유지해야 하는 제목, 날짜, 숫자, 항목 등을 선정했으므로, 여러 문장이 있는 문단의 분리 성능 전체를 평가한 결과는 아니다. 보고서 입력은 기존 Docling 추출 결과를 사용했으며 AI #27의 출력은 아니다.

OpenNLP는 비교한 모델에서 날짜를 마침표마다 나누거나 인용문을 중간에서 나누는 사례가 있었다. 기존 정규식 구현도 보고서의 `참고 1. ...` 형식을 중간에서 나누는 사례가 있었다. KiwiJava는 선정한 보고서 사례를 모두 기대한 단위로 유지했다.

따라서 비교한 사례에서 불필요한 분리가 적었고, 원문 위치를 받아 서비스의 텍스트 범위와 연결할 수 있는 KiwiJava를 선택했다. 정규식 예외를 계속 늘리는 부담을 줄이는 대신, 모델 로딩과 네이티브 라이브러리 배포 설정을 관리하기로 했다.

다만 KiwiJava가 기존 테스트와 다르게 처리한 사례도 있었다. 종결 문장부호가 없는 `교육을 실시했다 만족도 조사를 진행했다`를 두 문장으로 나눴는데, 서비스에서는 불확실한 경계를 임의로 확정하지 않고 원문 구간을 유지하기로 했다.

이에 종결 문장부호 없이 추정한 경계는 다시 합치고, 경계가 불확실하다는 경고를 남기도록 보완했다. 텍스트 단위는 입력 문자열에서 직접 잘라 생성하고, 위치는 해당 문단이나 셀의 `text`를 기준으로 Unicode 코드 포인트 단위로 기록한다.

`SENTENCE`, `FRAGMENT` 구분은 분석 처리에 다르게 사용해야 한다는 요구 근거를 확인하지 못해 제거했다.

Kiwi 모델은 자동 다운로드하고 배포 이미지에 포함한다. `ReportBodyConfig`에서 Kiwi 객체를 Bean으로 관리하고 서버 종료 시 자원을 정리한다.

이번 비교는 보고서 한 개와 제한된 사례를 사용했다. 향후 여러 문장이 포함된 문단과 다른 보고서에서 문제가 확인되면 샘플과 테스트를 추가해 재검토한다.

## 4. 검증 누락을 막으면서 엔티티의 의존성을 줄일 수 있는가

`ReportContent`가 `BodyValidator`를 직접 호출하면 검증 누락은 막을 수 있지만, 저장 엔티티가 본문 검증 구현을 직접 알게 된다.

반대로 호출자가 검증하기로만 약속하면 생성이나 교체 경로에서 검증을 빠뜨릴 수 있다.

이를 해결하기 위해 `ValidatedReportBody`를 도입했다.

- 검증을 통과해야 `ValidatedReportBody`를 생성할 수 있다.
- `BodyAssembler`는 검증된 객체를 반환한다.
- `ReportContent`의 생성과 본문 교체는 검증된 객체만 받는다.
- 엔티티는 검증기를 직접 호출하지 않고 내부 `ReportBody`를 꺼내 사용한다.

`ValidatedReportBody`는 별도 DB 엔티티가 아니라 검증을 통과한 본문을 담는 객체다. 조립 후 저장할 때 같은 검증을 반복하지 않으면서, 생성·교체 메서드의 입력 타입으로 검증 여부를 드러낸다.

본문 오류는 별도 `ContentValidationException`과 내부 코드 대신 기존 `ReportException`, `ReportErrorCode`로 통일했다. 검증 실패 위치를 실제 내부 로그에 연결하는 작업은 TODO로 남겼다.

## 5. 검증용 조회표를 어디까지 유지할 것인가

본문을 검사할 때 ID로 대상을 찾기 위해 여러 Map을 두었지만, 사용하지 않는 조회표까지 유지하면 원본 구조와 관리 대상이 중복된다.

실제로 사용하지 않던 `blocks`, `sections` 조회표는 제거했다.

다음 정보는 검증에서 사용하므로 유지했다.

- `types`: ID 중복과 참조 대상 종류 검사
- `texts`: ID로 문단이나 셀의 기준 텍스트 조회

`texts`를 유지한 이유는 단순히 조회 속도가 빠르기 때문만은 아니다. 참조된 텍스트의 범위를 검사할 때 원본 블록과 셀을 매번 순회하는 코드를 줄일 수 있다.

이 조회표는 본문 검증 시 생성하는 임시 구조이며, DB에 별도로 저장하거나 본문과 독립적으로 갱신하는 데이터는 아니다.

이름은 DB 인덱스와 혼동하지 않도록 `BodyIdRegistry`로 정리했다. 향후 Unit을 반복 조회할 필요가 생기면 소속 블록과 셀 위치까지 찾을 수 있도록 확장을 검토한다는 TODO를 남겼다.

## 6. 본문은 JsonNode와 ReportBody 중 어떤 타입으로 저장할 것인가

`ReportContent.content`의 `JsonNode`는 임시로 정한 타입이었다. 공통 본문 구조가 정해진 뒤에도 이를 유지하면 엔티티가 어떤 형태의 JSON을 저장하는지 Java 타입만으로 알기 어렵다.

따라서 Java 필드를 `ReportBody`로 구체화했다. DB 컬럼은 기존 JSONB를 유지하며, Hibernate가 객체를 JSON으로 변환해 저장하고 조회 시 다시 객체로 복원한다.

다음 사항을 확인하는 저장·재조회 통합 테스트를 추가했다.

- 공통 본문 예제의 필드가 저장 후에도 유지되는지
- 기존 계약 JSON을 저장한 행을 `ReportBody`로 읽을 수 있는지
- 문자열의 공백, 줄바꿈, 이모지와 텍스트 범위가 유지되는지
- 초안 교체 시 고정된 기준 본문이 바뀌지 않는지

JSON 문서 자체의 들여쓰기와 키 순서는 보존 대상이 아니다. 보고서 내용인 문자열 내부의 공백과 줄바꿈은 보존해야 한다.

본문 전체를 JSONB로 읽고 쓰는 비용은 타입 변경만으로 해결되지 않는다. 실제 편집 저장 방식과 성능 측정 결과에 따라 저장 단위와 갱신 방식을 재검토하도록 TODO를 남겼다.

`BodyJson`은 JSON과 공통 본문 사이의 변환을 담당한다. Hibernate의 DB 저장을 위해 반드시 거쳐야 하는 클래스는 아니다.

## 7. 검증용 API 호출 코드를 나중에도 사용할 수 있는가

실제 연동 검증을 위한 HTTP 코드와 운영용 호출 코드를 각각 만들면 같은 요청·응답 처리가 중복된다.

`PdfParser` 인터페이스와 최소 HTTP 구현인 `HttpPdfParser`를 만들고, 통합 테스트에서도 이 구현을 사용했다. #53에서는 이 코드를 접수 서비스에 연결하고 필요한 운영 처리를 추가한다.

호출 경계에서는 다음을 확인한다.

- 요청과 응답의 보고서 ID, 파싱 시도 ID 일치
- 원본 SHA-256 일치
- 성공 상태와 처리 시각의 유효성
- 지원하는 추출 스키마 버전
- 실패 응답의 오류 코드, HTTP 상태, 후속 행동 일치

AI가 계약에 맞게 반환한 실패는 `PdfParseResponse.Failed`로 보존한다. 통신 실패, 응답 대기시간 초과, 계약에 맞지 않는 응답은 `ReportException`으로 구분한다.

자동 재전송은 하지 않는다. Spring의 대기시간 초과가 AI 작업 종료를 의미하지 않기 때문이다. `Retry-After`와 후속 행동은 보존하되 실제 재시도 판단과 새 시도 생성은 #53에서 연결한다.

Java 클라이언트의 HTTP/2 전환 요청을 현재 Uvicorn 실행 환경이 처리하지 못하는 문제도 확인했다. HTTP/1.1에서는 정상적인 JSON 응답을 받았으므로 현재 호출은 HTTP/1.1로 고정했다.

향후 통신 병목이 확인되면 AI 서버와 프록시 설정을 함께 검토한다.

## 8. 셀 겹침은 파서 표현 방식인가, 추출 오류인가

실제 보고서 연동 중 AI가 성공으로 반환한 표를 Spring이 셀 겹침으로 거절했다.

처음에는 병합 셀 내부의 빈 자리를 별도 셀로 표현하는 형식일 가능성도 검토했다. 원본 PDF, 파서 구현, 기존 병합 셀 테스트와 PyMuPDF 원시 탐지 결과를 대조했다.

확인 결과는 다음과 같다.

- 파서는 실제 셀만 `cells`에 기록하고, 병합에 포함된 자리는 `rows`의 빈 문자열로 유지한다.
- 원본의 `통계목 1`은 3행 × 1열 병합 셀이다.
- 탐지 결과에서는 3행 × 2열로 범위가 넓어져 오른쪽 셀과 겹친다.
- 오른쪽 `소계`, `세부1`, `세부2`는 원본에서 별개의 셀이다.
- PyMuPDF의 기본 탐지 단계부터 겹침이 존재하며, 기존 파서의 보정에서도 해소되지 않는다.

따라서 Spring이 셀 표현 방식을 다르게 해석한 문제가 아니라 표 구조 추출 문제로 판단했다. 인접 셀을 삭제하는 대신 병합 범위와 셀별 내용 배치를 복원해야 한다.

`snap_tolerance`를 기본값 3에서 1로 변경한 비교 실험에서는 해당 표의 겹침이 사라졌다. 다만 다른 문서에 대한 영향은 검증하지 않았으므로 수정안으로 확정하지 않았다.

기존 파서 수정은 별도 버그 이슈로 분리했다. AI #27에는 셀 위치, 병합 크기, 표 범위 초과, 셀 겹침을 검사하는 최소 검증을 추가했다. 이 검증에 실패하면 HTTP 500 / `PARSER_FAILED` / `STOP`으로 반환한다.

AI 검증은 추출 결과의 기본 구조를 검사하고, Spring 검증은 공통 본문으로 변환된 결과의 규칙을 검사한다. 검사 대상과 책임이 달라 양쪽 검증을 유지했다.

## 9. 검증 결과와 남은 작업

2026-10-21 기준 검증 결과는 다음과 같다.

| 검사 | 결과 |
|---|---|
| Spring HTTP 호출·응답 처리 테스트 | 47개 통과 |
| 실제 AI API 연동 테스트 | 6개 통과 |
| 실제 정상 PDF 2개 | 공통 본문 변환, 원문과 경고 보존 확인 |
| 셀 겹침 PDF | `PARSER_FAILED / STOP`과 요청 ID 유지 확인 |
| URL 만료, 해시 불일치, 손상 PDF | 지정된 실패 응답 확인 |
| 계약 스키마와 예제 하네스 검사 | 통과 |

실제 AI API, 서비스, 자식 프로세스 파서를 실행했다. S3 다운로드만 로컬 PDF를 반환하는 테스트 전송 계층으로 대체했으므로 실제 S3 접근과 서명 URL 검증은 포함하지 않는다.

셀 겹침 PDF는 실패 응답 처리를 검증한 것이다. 해당 PDF의 정상 파싱과 본문 변환이 완료됐다는 의미는 아니다.
