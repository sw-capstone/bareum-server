# 이메일 인증 구현 초안과 협의 사항

- 상태: 구현 초안 / 팀 확정 아님
- 소유 역할: backend-team, frontend-team
- 최신 확인일: 2026-10-09 (이전 검증 결과는 날짜별 항목에 보존)
- 관련 작업: GitHub #12, 기존 이메일 조회 PR #11
- 목적: 명세 근거, 구현 초안, 협의 사항과 검증 결과 기록
- 공식 결정 ID는 발급하지 않은 작업 메모

## 명세에 확인된 사항

- 인증 목적은 SIGNUP / PASSWORD_RESET으로 구분한다.
- 회원가입 목적은 이메일·구글 가입 계정의 중복을 확인한다.
- 비밀번호 재설정은 이메일·비밀번호로 로그인 가능한 계정 대상이다.
- 인증 요청, 검증값, 만료일시를 email_verification에 저장한다.
- 인증번호 원문은 API 응답과 로그에 노출하지 않는다.
- 재발송 시 이전 번호를 교체하고 만료일시와 마지막 발송 시각을 갱신한다.
- 재발송으로 인증 실패 횟수를 초기화하지 않는다.
- 기술 정책서의 회원가입 인증번호 유효기간은 5분이다.
- 기술 정책서의 인증 완료 후 가입 가능 시간은 10분이다.

## 협의할 쟁점과 선택지

- 이메일 비교: 현재 대소문자 무시 기준의 정책 확정과 DB 중복 제약 적용. 조회와 실제 발송 주소의 구분은 아래 2026-10-09 항목을 따른다.
- 발송 제한: 최소 간격, 횟수, 집계 기간, 이메일·목적·IP 등의 집계 범위.
- 비밀번호 재설정: 인증번호와 인증 완료 증명의 유효기간.
- 인증 실패: 허용 횟수와 제한 이후의 처리 및 새 요청을 통한 우회 방지.
- 계정 상태: 탈퇴·제한 계정의 가입 및 비밀번호 재설정 처리.
- 인증 완료 요청: 재발송 허용 여부.
- API 계약: 요청·응답 필드, HTTP 상태, 오류 코드와 사용자 안내.
- 운영 메일 발송: 사용할 서비스·공용 계정, 발신 주소, 메일 문구. 개발 Gmail 설정과 수신 검증 결과는 아래 최신 항목을 따른다.

## 문서 충돌

- AUTH-001: 비밀번호 길이 8~12자.
- 기술 정책 명세서: 비밀번호 최소 12자.
- API 문서에는 계정 존재 노출 방지 안내가 미정으로 남아 있으나,
  화면 기획에는 이미 가입됨·가입되지 않음 안내가 기재되어 있다.
- 상충하는 내용을 팀 확정 사항으로 임의 통합하지 않는다.

## 구현상 보완할 사항

- email_verification 행 개수는 재발송을 포함한 실제 발송 횟수가 아니다.
- 재발송 시 기존 행을 갱신하므로 별도 발송 이력이나 카운터 구조를 검토한다.
- 동시에 요청이 들어와도 발송 제한을 우회하지 못하도록 처리해야 한다.
- 새 발송 요청으로 인증 실패 횟수 제한을 우회할 수 없는지 확인한다.
- SMTP 발송 성공과 DB 저장 성공은 하나의 원자적 작업이 아니므로
  실패 시 기록과 재시도 처리를 검토한다.
- DB 통합 테스트·SMTP 프로토콜 테스트와 실제 Gmail 수신 검증은 아래 검증 결과에 기록한다. 운영 제공자·계정의 전달 검증은 별도로 남아 있다.

## 재검토 조건

- 팀이 관련 정책 또는 API 계약을 확정할 때.
- 프론트 입력·응답 계약이나 인증수단 모델이 변경될 때.
- 재발송·인증 확인·가입 완료 서비스를 연결할 때.
- 메일 서비스 설정 및 실제 발송 테스트를 진행할 때.

## 별도 발송 기록 구조 제안

- email_verification_send_log 테이블과 엔티티·저장소를 추가한다.
- 재발송으로 인증 행을 갱신해도 발송 이력을 유지하기 위한 구현 초안이다.
- 이메일·목적·발송 시각을 기록하며 인증번호 원문은 저장하지 않는다.
- 발송 성공 처리 시 기록을 추가하는 방식으로 제안한다.
- 성공한 발송만 제한 횟수에 포함할지, 집계 범위와 보관기간은 미확정이다.
- SMTP 발송과 DB 기록 사이의 실패 처리 및 동시 요청 제어는 별도 구현한다.

## 발송 제한 집계 초안

- 별도 발송 기록을 이메일 기준으로 집계한다.
- 이메일 대소문자를 구분하지 않으며 인증 목적별 발송을 합산한다.
- 시간당 제한은 현재 시각부터 과거 1시간을 기준으로 한다.
- 일당 제한은 현재 시각부터 과거 24시간을 기준으로 한다.
- 기간 시작 시각과 같은 발송 기록도 횟수에 포함한다.
- 설정된 최대 횟수에 도달하면 다음 발송을 차단한다.
- 최소 대기시간이 정확히 지난 시각부터 발송을 허용한다.
- 위 집계 방식은 팀 미확정 구현 초안이며 제한 수치는 입력하지 않는다.
- 최초 발송은 아래 advisory lock으로 직렬화한다. 재발송·인증 확인에서도 같은 잠금 기준을 사용해야 한다.

## 동시 요청 제어 초안

- PostgreSQL 트랜잭션 단위 advisory lock을 사용한다.
- 기존 IgnoreCase 조회와 맞추기 위해 DB의 upper(email)을 기준으로 한다.
- 이메일 인증 전용 접두사와 SHA-256으로 64비트 잠금 키를 생성한다.
- 잠금은 기존 트랜잭션 안에서 획득하고 트랜잭션 종료 시 해제한다.
- 최초 발송과 재발송이 같은 잠금 규칙을 사용해야 한다.
- 제한 확인과 발송 기록 저장까지 잠금을 유지하도록 연결한다.
- 64비트 키가 충돌하면 다른 이메일도 같은 잠금을 기다릴 수 있다.
- 잠금 대기 및 메일 발송 타임아웃은 별도로 검토한다.
- 이 방식은 구현 초안이며 실제 동시 요청 검증은 아직 수행하지 않았다.

## 시간 계산 방식

- 이메일 인증 서비스는 UTC 기준 Clock을 주입받아 시각을 계산한다.
- 만료 시각과 발송 시각의 계산 기준을 통일하고 테스트에서 시간을 고정하기 위한 구현 선택이다.
- 인증 유효기간·재발송 제한 수치를 확정하는 내용은 아니다.

## 최초 발송 서비스 연결 초안

- 설정 확인 후 이메일 잠금, 계정 확인, 발송 제한 확인을 수행한다.
- READ_COMMITTED 트랜잭션으로 제한 확인과 기록 저장을 연결한다.
- 최초 발송 API 호출마다 새 인증 요청 행을 생성한다.
- 같은 이메일·목적의 최신 요청에서 실패 횟수를 이어받는다.
- 만료되거나 사용된 과거 요청의 실패 횟수도 현재는 이어받는다.
  실패 횟수 초기화 시점은 협의 후 수정해야 한다.
- 새 요청 생성 시 기존 인증번호·인증 완료 증명의 처리 범위는
  인증 확인·최종 사용 서비스 연결 전에 확정해야 한다.
- 인증번호 원문은 메일 전달에만 사용하고 DB에는 해시를 저장한다.
- 발송 전 기록을 준비하고, SMTP 수락 후 측정한 시각으로 발송 기록을 갱신한다.
- 메일 발송 전에 인증 요청과 발송 기록의 DB 변경을 flush한다.
- 메일 발송 실패 시 DB 변경을 롤백한다. SMTP 수락 후 유효기간을 계산하며, 성공 후 만료를 이유로 기록을 롤백하지 않는다.
- expiresIn은 응답 시점의 남은 시간을 초 단위로 올림하여 반환한다.
- 위 처리 방식과 오류 매핑은 구현 초안이다.

## SMTP와 DB 처리의 한계

- SMTP 발송은 DB 트랜잭션으로 되돌릴 수 없다.
- 메일 전달 후 DB 커밋이 실패하면 기록이 없는데 메일이 도착할 수 있다.
- SMTP 오류가 발생해도 메일 서버의 수락 여부가 불명확할 수 있다.
- 실제 발송 전 타임아웃, 실패 기록, 재시도 및 중복 처리 방식을 검토한다.
- SMTP 요청 성공은 수신함 도착을 보장하지 않는다.

### HTTP 계약

- 기존 빈 `EmailVerificationSendController`를 구현해 POST 요청을 검증한 뒤
  기존 `EmailVerificationSendService.send()`에 전달한다.
- 요청 DTO의 email·purpose와 기존 expiresIn 응답을 유지한다.
  성공 응답은 기존 조회 Controller 패턴과 같은 HTTP 200으로 연결한 구현 초안이다.
- expiresIn은 응답 시점에 남은 초를 올림한 값이며 항상 300인 것은 아니다.
- 인증번호 원문·해시·인증 엔티티를 HTTP 응답으로 반환하지 않는다.
- 일반 요청 오류와 필드 검증 오류를 모두 표현하도록 공통 OpenAPI에
  BadRequestProblemDetail(anyOf)을 추가하고 AUTH-005 문서에서 참조한다.
- 발송 제한 값, 메일 제공자·발신 계정, 비밀번호 재설정 기간은 새로 정하지 않는다.
- 발송 기록 테이블과 기존 migration은 변경하지 않는다.
- 서비스·제한·잠금·해시 테스트는 이미 존재하지만 SMTP 구현과 코드 생성기의
  독립 테스트 및 실제 메일 서비스 검증은 별도로 남아 있다.
- 잠금 획득·커밋/롤백 후 해제 테스트는 존재한다. 전체 발송의 동시 요청 시나리오는
  별도 검증이 필요하다. 앞선 초안의 '실제 동시 요청 검증 미수행'과 구분한다.

### DB의 대소문자 무시 중복 제약: 검토안

쟁점은 `UNIQUE(email)`만으로 대소문자만 다른 계정의 동시 저장을 막을 수 없다는 점이다.
조회 단계와 이메일 잠금만으로 DB 전체의 중복 방지를 보장하지 않는다.

| 선택지 | 영향 | 적용 조건 |
|---|---|---|
| 표현식 unique index | 기존 IgnoreCase 조회·잠금의 `upper(email)`과 DB 비교 기준을 맞춘다. 모든 가입 경로에서 중복 저장을 차단한다 | 기존 데이터 중복과 DB 문자 비교 규칙 확인, 계정·탈퇴 정책 확정 후 새 Flyway migration 추가 |
| 정규화한 이메일 별도 컬럼 | 원래 등록 주소를 보존하면서 비교 기준을 명시할 수 있다 | 컬럼·backfill·모든 쓰기 경로 변경 및 기존 데이터 정리 필요 |
| 현재 제약 유지 | DB 변경은 적으나 대소문자만 다른 중복이 저장될 위험이 남는다 | 최종 해결로 간주하지 않고 가입 경로의 동시성 방어와 함께 재검토 |

표현식 index를 선택한다면 먼저 중복을 확인한다.

```sql
SELECT upper(email) AS comparison_email, count(*) AS account_count
FROM member
GROUP BY upper(email)
HAVING count(*) > 1;
```

중복이 없고 전체 회원 상태에 같은 제약을 적용하기로 합의한 경우의 후보 SQL이다.

```sql
CREATE UNIQUE INDEX uk_member_email_ignore_case ON member (upper(email));
```

- 기존 중복 계정은 자동 삭제·병합하지 않는다. 탈퇴 계정의 주소 재사용 여부도 먼저 결정한다.
- 정책·기존 데이터 확인 전이므로 이번 변경에는 index와 migration을 적용하지 않았다.
- 적용 시 대소문자만 다른 동시 가입, 구글·이메일 가입 충돌과 제약 위반의 오류 응답을 검증한다.
  기존 migration을 고치지 않고 새 버전으로 추가한다.
- 참고: [PostgreSQL 표현식 index](https://www.postgresql.org/docs/17/indexes-expressional.html).

### 발송 지연·롤백과 Outbox: 현재 수정 및 검토안

- 최초 발송은 SMTP 호출이 성공적으로 반환된 시각부터 코드 유효기간을 계산한다.
  발송 지연으로 가입용 5분이 소진된 뒤 성공 응답 대신 예외가 발생하던 경로를 수정했다.
- 인증 요청과 이력을 발송 전에 flush하고, 수락 시각·만료 시각을 갱신해 함께 커밋한다.
  수락 직후 시계가 만료 시각 이후로 이동해도 성공 기록은 유지하고 `expiresIn: 0`을 반환한다.
  이 경우 재발송 안내가 필요하며 화면·오류 계약을 함께 검토한다.
- SMTP 실패 시 롤백은 유지한다. **SMTP 수락 후 DB 커밋 실패와 수락 여부가 불명확한 통신 실패는
  여전히 해결되지 않았다.** SMTP 성공은 실제 수신함 도착도 보장하지 않는다.

| 선택지 | 영향 | 재검토 조건 |
|---|---|---|
| 현재 동기 발송 + 유효기간·타임아웃 보완 | 현재 성공 응답을 유지한다. 발송 중 DB 트랜잭션·잠금은 계속 유지되며 SMTP·DB 불일치가 남는다 | 실제 서비스 연동 전 커밋 실패·수락 불명확·잠금 대기 정책 확인 |
| Transactional Outbox + 별도 worker | 인증 요청과 발송 작업을 같은 DB 트랜잭션으로 저장하고, 커밋 후 worker가 SMTP를 호출한다. 네트워크 요청을 DB 잠금 밖으로 분리할 수 있다 | 작업 상태·대기 중 발송 제한·재시도·중복·유효기간과 API 응답을 팀·프론트와 합의 |

Outbox 도입 전에 다음 사항을 정해야 한다.

- 인증번호 해시만으로 메일 본문을 복원할 수 없다. 발송용 코드를 보관한다면 암호화·키 관리·
  접근 제한·전달 후 삭제가 필요하며 원문을 로그나 평문 작업 payload에 남기지 않는다.
- QUEUED/SENT/FAILED 상태와 제한 횟수 예약·실패 해제·최대 재시도·보관기간을 정의한다.
- 최초 대기 시작 또는 SMTP 수락 중 어느 시각에 유효기간을 시작할지 정한다.
  비동기 접수 응답(예: 202)과 상태 조회를 도입하면 현재 200·expiresIn 계약과 프론트 타이머를 변경해야 한다.
- 재시도에서 같은 코드·작업 ID를 사용해 중복 작업을 억제한다. SMTP 수락 후 기록 실패·응답 유실은
  전달 중복 가능성을 남기므로 정확히 한 번 전달을 보장한다고 표현하지 않는다.
- 재발송·인증 확인·증명 소비와 최신 요청의 우선순위도 함께 검토한다.
- Outbox·worker는 이번 변경에 구현하지 않았으며, 합의 후 별도 migration과 검증을 추가한다.

### SMTP 설정과 환경변수

개발 검증에는 Gmail SMTP를 사용한다. 운영 메일 서비스·공용 발신 계정은 별도 결정 사항이다.
개발용 주소와 앱 비밀번호는 외부 설정으로 주입하며 공유 문서·저장소에 실제 값을 남기지 않는다.
개발 검증 결과를 운영 제공자·계정의 확정이나 운영 발송 검증으로 취급하지 않는다.

| 설정 | 주입 방법 | 의미 |
|---|---|---|
| `spring.mail.host` | `SPRING_MAIL_HOST` | 합의한 제공자의 SMTP 호스트. 기본 제공자를 지정하지 않음 |
| `spring.mail.port` | `SPRING_MAIL_PORT` | 제공자가 요구하는 포트 |
| `spring.mail.username` / `password` | `SPRING_MAIL_USERNAME` / `SPRING_MAIL_PASSWORD` | 발신 계정의 인증 정보. 저장소·문서에 실제 값을 기록하지 않음 |
| `auth.email-verification.mail-from` | `EMAIL_VERIFICATION_MAIL_FROM` | 제공자에서 승인한 발신 주소. 누락 시 발송 차단 |
| `auth.email-verification.hash-secret` | `EMAIL_VERIFICATION_HASH_SECRET` | 인증번호 HMAC 키. 제공자 비밀번호와 별도로 주입 |
| `mail.smtp.connectiontimeout` | `SMTP_CONNECTION_TIMEOUT_MS` | 연결 대기 제한. 구현 기본값 5000ms |
| `mail.smtp.timeout` | `SMTP_READ_TIMEOUT_MS` | 응답 읽기 대기 제한. 구현 기본값 5000ms |
| `mail.smtp.writetimeout` | `SMTP_WRITE_TIMEOUT_MS` | 쓰기 대기 제한. 구현 기본값 5000ms |

- 타임아웃 5000ms는 무한 대기를 방지하기 위한 구현 초안이다. 제공자·운영 기준에 맞춰 재검토한다.
  세 타임아웃은 개별 통신 단계 제한이며 요청 전체 처리시간이나 DB 잠금 대기의 상한을 보장하지 않는다.
- SMTP AUTH·STARTTLS·implicit TLS 여부는 제공자 지침에 맞춰 배포 설정에 추가한다.
  다음은 AUTH와 STARTTLS 방식일 때 사용하는 설정 형태이며, 특정 서비스를 선택하는 값이 아니다.

```yaml
spring:
  mail:
    properties:
      "[mail.smtp.auth]": ${SMTP_AUTH}
      "[mail.smtp.starttls.enable]": ${SMTP_STARTTLS_ENABLED}
      "[mail.smtp.starttls.required]": ${SMTP_STARTTLS_REQUIRED}
```

- implicit TLS 제공자라면 해당 포트·`mail.smtp.ssl.enable`을 별도로 설정하고 연결을 검증한다.
  비밀번호는 Secret 설정으로 주입하며 SMTP 디버그 로그에 인증 정보·코드가 노출되지 않게 한다.
- `auth.email-verification.minimum-send-interval-seconds`, `max-sends-per-hour`, `max-sends-per-day`는
  팀이 정한 양수 값을 외부 설정에 넣어야 한다. 비밀번호 재설정에는 `password-reset-code-ttl-seconds`도 필요하다.
  미정 항목에 운영 기본값을 넣지 않으며, 누락 시 기존 AUTH-0006 차단을 유지한다.
- 설정 객체는 final 필드와 생성자 바인딩으로 변경했다. 가입용 300초 기본값과 조회 getter를 유지하고
  setter를 제거해 실행 중 변경되지 않도록 했다.
- 참고: [Spring Boot 메일 설정](https://docs.spring.io/spring-boot/reference/io/email.html),
  [생성자 설정 바인딩](https://docs.spring.io/spring-boot/reference/features/external-config.html).

### 설정 방법

- `gmail-verification` 프로필을 명시적으로 활성화할 때만 Gmail 설정을 적용한다.
  기본 설정의 SMTP 제공자는 지정하지 않는다.
- `smtp.gmail.com:587`에 SMTP AUTH와 STARTTLS 필수를 적용하고 서버 인증서를 확인한다.
  통신 타임아웃은 공통 설정의 값을 사용하며 검증·운영 조건에 맞게 외부에서 재정의할 수 있다.
- `GMAIL_TEST_ADDRESS`: 개발 검증 발신 주소. 같은 계정의 수신함으로 검증할 수 있다.
- `GMAIL_APP_PASSWORD`: 해당 계정에서 발급한 앱 비밀번호. 일반 Google 계정 비밀번호를 사용하지 않는다.
  앱 비밀번호 발급에는 2단계 인증이 필요하며 계정 정책에 따라 발급이 제한될 수 있다.
- `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `EMAIL_VERIFICATION_HASH_SECRET`와 발송 제한 설정을 별도로 주입한다.
  비밀번호 재설정 검증에는 해당 목적의 코드 유효기간도 필요하다.
- 주소·비밀번호·인증번호는 공유 자료와 로그에 남기지 않는다. 프로필에서는 SQL 출력도 비활성화한다.
- 실제 검증은 API 요청, Gmail 수신 메일, 동일 요청의 DB 해시·주소·만료 시각·발송 이력을 함께 대조한다.
  수신 확인이 끝나기 전에는 실제 발송 검증 완료로 표시하지 않는다.
- 참고: [Gmail SMTP 설정](https://support.google.com/mail/answer/7104828?hl=ko),
  [Google 앱 비밀번호 안내](https://support.google.com/accounts/answer/185833?hl=ko).

### 설정 검증 결과

- `gradlew.bat check --no-daemon`: 전체 100개 통과, 실패·오류·건너뜀 0개.
- Gmail 프로필의 호스트·포트, SMTP AUTH·STARTTLS 필수·서버 인증서 확인,
  외부 발신 주소 주입과 공통 타임아웃 적용을 검증했다.
- Gmail 프로필에서도 운영 발송 제한 기본값을 추가하지 않았고, 기본 프로필은 제공자를 선택하지 않는다.
- 서버 실행 파일 빌드 통과. 실제 Gmail 수신 검증 결과는 아래 항목을 따른다.

### 실제 Gmail 수신·DB 대조 결과

- 비밀번호 재설정 발송 API의 HTTP 200 응답과 Gmail 수신함 도착을 확인했다.
- 요청 이메일의 대소문자를 다르게 입력해도 회원의 등록 주소로 발송되고,
  인증 요청·발송 이력에는 등록 주소와 `PASSWORD_RESET` 목적이 저장됨을 확인했다.
- 수신 메일의 인증번호로 계산한 HMAC-SHA256 해시가 DB의 `code_hash`와 일치했다.
  메일의 발신·수신 주소와 제목·본문도 확인했으며 실제 주소와 인증번호는 공유 자료에 기록하지 않는다.
- 인증 요청의 `last_sent_at`과 발송 이력의 `sent_at`이 일치하고,
  `expires_at - last_sent_at`이 검증용 유효기간 300초와 일치함을 확인했다.
- 검증에 사용한 발송 간격 60초, 시간당 5건·일당 10건 제한, 재설정 유효기간 300초는
  테스트 전용 값이다. 운영 발송 정책과 재설정 유효기간을 확정한 값이 아니다.
- 이번 결과는 Gmail을 통한 한 건의 발송·수신과 동일 요청의 DB 저장 검증이다.
  운영 제공자 검증, SMTP 수락 후 DB 커밋 실패 복구, Outbox·재시도·전달 중복 및 전체 동시성은 별도 과제다.
