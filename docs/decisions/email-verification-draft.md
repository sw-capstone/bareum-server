## 개발 서버 env v2 임시 정책 (2026-10-14)

아래 값은 개발 서버 배포 설정을 준비하기 위해 임의로 선택한 **팀 미확정 임시 정책**이다. Java의 운영 기본값으로 고정하지 않고 외부 설정으로 주입한다. 기존 검증에 사용한 수치와 구분하며 AWS 적용·실제 발송 검증은 별도로 진행한다.

| 항목 | 임시 적용값 | 선택 이유·팀 확인 사항 |
| --- | --- | --- |
| PASSWORD_RESET 인증번호 유효기간 | SMTP 수락 후 300초 | 회원가입 번호와 동일한 5분으로 초기 안내를 통일. 재설정 목적의 기간은 팀 확인 필요 |
| 최소 발송 간격 | 60초 | 메일 지연 시 재시도를 허용하면서 반복 접수 제한 |
| 동일 이메일 시간당 발송 제한 | 최근 60분 최대 5회 | 최초 요청과 재발송을 포함한 반복 발송 제한 |
| 동일 이메일 일일 발송 제한 | 최근 24시간 최대 20회 | 지속적인 반복 요청 제한. 제공자 한도·실제 이용량에 따라 재검토 |

**정책 문구의 임시 해석:** ‘인증 유효기간·재발송 - 5분’은 최초·재발송된 인증번호의 유효기간이 각각 5분이라는 의미로 우선 해석한다. 최소 재발송 대기는 별도 60초다. 이 해석은 팀 확정 사항이 아니며, 원문의 의도가 5분 대기라면 설정과 프론트 안내를 함께 조정한다.

```dotenv
AUTH_EMAILVERIFICATION_SIGNUPCODETTLSECONDS=300
AUTH_EMAILVERIFICATION_PASSWORDRESETCODETTLSECONDS=300
AUTH_EMAILVERIFICATION_MINIMUMSENDINTERVALSECONDS=60
AUTH_EMAILVERIFICATION_MAXSENDSPERHOUR=5
AUTH_EMAILVERIFICATION_MAXSENDSPERDAY=20
```

- 위 이름은 #18의 `auth.email-verification` 생성자 설정 바인딩에 직접 연결되는 환경변수다. 값 누락·0 이하일 때 기존 AUTH-0006 차단을 유지한다.
- 제한은 대소문자를 무시한 동일 이메일의 SIGNUP·PASSWORD_RESET 최초·재발송을 합산한다. 성공 이력과 Outbox 예약을 함께 반영하며 미성공 작업도 집계 기간 내 예약으로 남을 수 있다. SMTP 자동 재시도는 같은 작업으로 처리한다.
- 번호 300초는 인증 완료 후 PASSWORD_RESET 증명의 유효기간을 정한 것이 아니다. 증명 기간·인증 실패 제한·복구 흐름은 별도 협의 항목으로 남긴다.
- **영향·재검토 조건:** 실제 메일 지연, 사용자 재시도, 프론트 타이머와 제공자 발송 한도를 확인한다. 운영 적용이나 팀 정책 해석이 변경될 때 기간·제한·오류 안내를 함께 재검토한다.

## 명세에 확인된 사항

- 인증 목적은 SIGNUP / PASSWORD_RESET으로 구분한다.
- 회원가입 목적은 이메일·구글 가입 계정의 중복을 확인한다.
- 비밀번호 재설정은 이메일·비밀번호로 로그인 가능한 계정 대상이다.
- 인증 요청, 검증값, 만료일시를 email_verification에 저장한다.
- 인증번호 원문은 API 응답과 로그에 노출하지 않는다.
- 재발송 시 이전 번호를 교체하고 만료일시와 마지막 발송 시각을 갱신한다.
- 재발송으로 인증 실패 횟수를 초기화하지 않는다.
- 기술 정책서의 회원가입 인증번호 유효기간은 5분이다.
- 기술 정책서의 인증 완료 후 가입 가능 시간은 10분이다.

## 협의할 쟁점과 선택지

- 이메일 비교: 현재 대소문자 무시 기준의 정책 확정과 DB 중복 제약 적용. 조회와 실제 발송 주소의 구분은 아래 2026-10-09 항목을 따른다.
- 발송 제한: 최소 간격, 횟수, 집계 기간, 이메일·목적·IP 등의 집계 범위.
- 비밀번호 재설정: 인증번호와 인증 완료 증명의 유효기간.
- 인증 실패: 허용 횟수와 제한 이후의 처리 및 새 요청을 통한 우회 방지.
- 계정 상태: 탈퇴·제한 계정의 가입 및 비밀번호 재설정 처리.
- 인증 완료 요청: 재발송 허용 여부.
- API 계약: 요청·응답 필드, HTTP 상태, 오류 코드와 사용자 안내.
- 운영 메일 발송: 사용할 서비스·공용 계정, 발신 주소, 메일 문구. 개발 Gmail 설정과 수신 검증 결과는 아래 최신 항목을 따른다.

## 문서 충돌

- AUTH-001: 비밀번호 길이 8~12자.
- 기술 정책 명세서: 비밀번호 최소 12자.
- API 문서에는 계정 존재 노출 방지 안내가 미정으로 남아 있으나,
  화면 기획에는 이미 가입됨·가입되지 않음 안내가 기재되어 있다.
- 상충하는 내용을 팀 확정 사항으로 임의 통합하지 않는다.

## 구현상 보완할 사항

- email_verification 행 개수는 재발송을 포함한 실제 발송 횟수가 아니다.
- 재발송 시 기존 행을 갱신하므로 별도 발송 이력이나 카운터 구조를 검토한다.
- 동시에 요청이 들어와도 발송 제한을 우회하지 못하도록 처리해야 한다.
- 새 발송 요청으로 인증 실패 횟수 제한을 우회할 수 없는지 확인한다.
- SMTP 발송 성공과 DB 저장 성공은 하나의 원자적 작업이 아니므로
  실패 시 기록과 재시도 처리를 검토한다.
- DB 통합 테스트·SMTP 프로토콜 테스트와 실제 Gmail 수신 검증은 아래 검증 결과에 기록한다. 운영 제공자·계정의 전달 검증은 별도로 남아 있다.

## 재검토 조건

- 팀이 관련 정책 또는 API 계약을 확정할 때.
- 프론트 입력·응답 계약이나 인증수단 모델이 변경될 때.
- 재발송·인증 확인·가입 완료 서비스를 연결할 때.
- 메일 서비스 설정 및 실제 발송 테스트를 진행할 때.

## 별도 발송 기록 구조 제안

- email_verification_send_log 테이블과 엔티티·저장소를 추가한다.
- 재발송으로 인증 행을 갱신해도 발송 이력을 유지하기 위한 구현 초안이다.
- 이메일·목적·발송 시각을 기록하며 인증번호 원문은 저장하지 않는다.
- 발송 성공 처리 시 기록을 추가하는 방식으로 제안한다.
- 성공한 발송만 제한 횟수에 포함할지, 집계 범위와 보관기간은 미확정이다.
- SMTP 발송과 DB 기록 사이의 실패 처리 및 동시 요청 제어는 별도 구현한다.

## 발송 제한 집계 초안

- 별도 발송 기록을 이메일 기준으로 집계한다.
- 이메일 대소문자를 구분하지 않으며 인증 목적별 발송을 합산한다.
- 시간당 제한은 현재 시각부터 과거 1시간을 기준으로 한다.
- 일당 제한은 현재 시각부터 과거 24시간을 기준으로 한다.
- 기간 시작 시각과 같은 발송 기록도 횟수에 포함한다.
- 설정된 최대 횟수에 도달하면 다음 발송을 차단한다.
- 최소 대기시간이 정확히 지난 시각부터 발송을 허용한다.
- 위 집계 방식은 팀 미확정 구현 초안이며 제한 수치는 입력하지 않는다.
- 최초 발송은 아래 advisory lock으로 직렬화한다. 재발송·인증 확인에서도 같은 잠금 기준을 사용해야 한다.

## 동시 요청 제어 초안

- PostgreSQL 트랜잭션 단위 advisory lock을 사용한다.
- 기존 IgnoreCase 조회와 맞추기 위해 DB의 upper(email)을 기준으로 한다.
- 이메일 인증 전용 접두사와 SHA-256으로 64비트 잠금 키를 생성한다.
- 잠금은 기존 트랜잭션 안에서 획득하고 트랜잭션 종료 시 해제한다.
- 최초 발송과 재발송이 같은 잠금 규칙을 사용해야 한다.
- 제한 확인과 인증 요청·Outbox 저장까지만 잠금을 유지한다. worker의 확인·성공 기록은 별도 짧은 트랜잭션이며 SMTP 호출 중에는 잠금을 유지하지 않는다.
- 64비트 키가 충돌하면 다른 이메일도 같은 잠금을 기다릴 수 있다.
- 잠금 대기 및 메일 발송 타임아웃은 별도로 검토한다.
- 잠금·발송 동시성의 검증 범위는 날짜별 최종 검증 결과를 따른다.

## 시간 계산 방식

- 이메일 인증 서비스는 UTC 기준 Clock을 주입받아 시각을 계산한다.
- 만료 시각과 발송 시각의 계산 기준을 통일하고 테스트에서 시간을 고정하기 위한 구현 선택이다.
- 인증 유효기간·재발송 제한 수치를 확정하는 내용은 아니다.

## 최초 발송 서비스 연결 초안

- 설정 확인 후 이메일 잠금, 계정 확인, 발송 제한 확인을 수행한다.
- READ_COMMITTED 트랜잭션으로 제한 확인과 기록 저장을 연결한다.
- 최초 발송 API 호출마다 새 인증 요청 행을 생성한다.
- 같은 이메일·목적의 최신 요청에서 실패 횟수를 이어받는다.
- 만료되거나 사용된 과거 요청의 실패 횟수도 현재는 이어받는다.
  실패 횟수 초기화 시점은 협의 후 수정해야 한다.
- 새 요청 생성 시 기존 인증번호·인증 완료 증명의 처리 범위는
  인증 확인·최종 사용 서비스 연결 전에 확정해야 한다.
- 검증용 해시는 email_verification에 저장하고, 발송용 코드는 AES-256-GCM으로 암호화해 Outbox에 저장한다.
- 인증 요청과 Outbox를 함께 커밋하며 커밋 전 SMTP를 호출하지 않는다.
- 별도 worker가 SMTP를 호출하고 수락 시각·만료 시각·성공 이력·작업 완료를 함께 커밋한다.
- SMTP 실패는 인증 요청을 롤백하지 않고 재시도·최종 실패 상태로 기록한다.
- 접수 응답의 expiresIn은 0이다. 성공 상태 조회에서 남은 유효시간을 초 단위로 올림해 반환한다.
- 위 처리 방식과 오류 매핑은 구현 초안이다.

## SMTP와 DB 처리의 한계

- SMTP 발송은 DB 트랜잭션으로 되돌릴 수 없다.
- 메일 전달 후 성공 기록 커밋이 실패하면 Outbox 작업은 남지만 성공 이력은 없을 수 있다. lease 만료 후 같은 작업·코드로 복구하며 전달 중복은 남을 수 있다.
- SMTP 오류가 발생해도 메일 서버의 수락 여부가 불명확할 수 있다.
- 타임아웃·실패·재시도·중복 처리의 현재 구현안과 재검토 조건은 아래 Outbox 항목을 따른다.
- SMTP 요청 성공은 수신함 도착을 보장하지 않는다.

## 2026-10-09 발송 리뷰 반영과 협의 사항

### 이메일 비교와 실제 수신 주소

- 계정 조회·중복 검사는 이메일 전체 주소의 대소문자를 구분하지 않는다.
  대소문자만 다른 주소를 별도 계정으로 가입할 수 없다는 의미이며, 가입·로그인·
  비밀번호 재설정·DB 제약에서 같은 기준을 사용해야 한다. 현재 구현 기준이고 팀 정책 확정이 필요하다.
- 비교용 정규화와 메일 전송 주소는 구분한다. 비밀번호 재설정은 IgnoreCase로 회원을 찾은 뒤
  회원의 등록 이메일을 그대로 사용해 메일을 발송하고 인증 요청·발송 이력을 저장한다.
- 회원가입 발송은 요청 주소를 그대로 사용한다. 공백 제거, 도메인별 점·더하기 별칭 통합 등은
  새로 도입하지 않는다. 이런 정규화가 필요하면 계정 동일성 정책과 함께 검토한다.

### DB의 대소문자 무시 중복 제약: 적용

- `upper(email)`을 사용하는 partial unique index를 새 Flyway migration으로 추가한다.
  기존 IgnoreCase 조회와 advisory lock의 비교 기준을 맞춘다.
- 중복 검사에는 탈퇴 이력도 조회하지만, `DELETED` 상태와 `withdrawn_at`이 모두 확인된
  계정은 주소를 점유하지 않는다. 나머지 상태는 index와 가입 중복 검사에 포함한다.
- 기존 `UNIQUE(email)`은 재가입을 차단하므로 partial index로 교체한다.
  기존 가입 서비스의 제약 위반 오류 매핑과 호환되도록 `member_email_key` 이름을 유지한다.
- 적용 전 테이블 쓰기를 잠그고 제약 대상의 대소문자 무시 중복을 확인한다.
  충돌하면 migration을 중단하며 기존 계정을 삭제·병합하거나 이메일을 수정하지 않는다.
- 탈퇴 이메일 재사용은 아래 2026-10-10 항목의 **팀 미확정 임시 정책**이다.
- 참고: [PostgreSQL 표현식 index](https://www.postgresql.org/docs/17/indexes-expressional.html),
  [partial index](https://www.postgresql.org/docs/17/indexes-partial.html).

### SMTP 설정과 환경변수

개발 검증에는 Gmail SMTP를 사용한다. 운영 메일 서비스·공용 발신 계정은 별도 결정 사항이다.
개발용 주소와 앱 비밀번호는 외부 설정으로 주입하며 공유 문서·저장소에 실제 값을 남기지 않는다.
개발 검증 결과를 운영 제공자·계정의 확정이나 운영 발송 검증으로 취급하지 않는다.

| 설정 | 주입 방법 | 의미 |
|---|---|---|
| `spring.mail.host` | `SPRING_MAIL_HOST` | 합의한 제공자의 SMTP 호스트. 기본 제공자를 지정하지 않음 |
| `spring.mail.port` | `SPRING_MAIL_PORT` | 제공자가 요구하는 포트 |
| `spring.mail.username` / `password` | `SPRING_MAIL_USERNAME` / `SPRING_MAIL_PASSWORD` | 발신 계정의 인증 정보. 저장소·문서에 실제 값을 기록하지 않음 |
| `auth.email-verification.mail-from` | `EMAIL_VERIFICATION_MAIL_FROM` | 제공자에서 승인한 발신 주소. 누락 시 발송 차단 |
| `auth.email-verification.hash-secret` | `EMAIL_VERIFICATION_HASH_SECRET` | 인증번호 HMAC 키. 제공자 비밀번호와 별도로 주입 |
| `mail.smtp.connectiontimeout` | `SMTP_CONNECTION_TIMEOUT_MS` | 연결 대기 제한. 구현 기본값 5000ms |
| `mail.smtp.timeout` | `SMTP_READ_TIMEOUT_MS` | 응답 읽기 대기 제한. 구현 기본값 5000ms |
| `mail.smtp.writetimeout` | `SMTP_WRITE_TIMEOUT_MS` | 쓰기 대기 제한. 구현 기본값 5000ms |

- 타임아웃 5000ms는 무한 대기를 방지하기 위한 구현 초안이다. 제공자·운영 기준에 맞춰 재검토한다.
  세 타임아웃은 개별 통신 단계 제한이며 요청 전체 처리시간이나 DB 잠금 대기의 상한을 보장하지 않는다.
- SMTP AUTH·STARTTLS·implicit TLS 여부는 제공자 지침에 맞춰 배포 설정에 추가한다.
  다음은 AUTH와 STARTTLS 방식일 때 사용하는 설정 형태이며, 특정 서비스를 선택하는 값이 아니다.

```yaml
spring:
  mail:
    properties:
      "[mail.smtp.auth]": ${SMTP_AUTH}
      "[mail.smtp.starttls.enable]": ${SMTP_STARTTLS_ENABLED}
      "[mail.smtp.starttls.required]": ${SMTP_STARTTLS_REQUIRED}
```

- implicit TLS 제공자라면 해당 포트·`mail.smtp.ssl.enable`을 별도로 설정하고 연결을 검증한다.
  비밀번호는 Secret 설정으로 주입하며 SMTP 디버그 로그에 인증 정보·코드가 노출되지 않게 한다.
- `auth.email-verification.minimum-send-interval-seconds`, `max-sends-per-hour`, `max-sends-per-day`는
  팀이 정한 양수 값을 외부 설정에 넣어야 한다. 비밀번호 재설정에는 `password-reset-code-ttl-seconds`도 필요하다.
  미정 항목에 운영 기본값을 넣지 않으며, 누락 시 기존 AUTH-0006 차단을 유지한다.
- 설정 객체는 final 필드와 생성자 바인딩으로 변경했다. 가입용 300초 기본값과 조회 getter를 유지하고
  setter를 제거해 실행 중 변경되지 않도록 했다.
- 참고: [Spring Boot 메일 설정](https://docs.spring.io/spring-boot/reference/io/email.html),
  [생성자 설정 바인딩](https://docs.spring.io/spring-boot/reference/features/external-config.html).

## 2026-10-11 Transactional Outbox 구현안

상태: 팀 미확정 구현안. [공유 AUTH-005 명세](https://app.notion.com/p/4f311880adea82bfa8b301d6b27b2b20)의
인증 목적·계정 검사·원문 비노출 원칙을 유지한다. 발송 상태 조회, 접수 응답과 worker 운영 기준은
명세에 확정된 계약이 없어 아래와 같이 구현했다. 프론트와 계약을 맞춘 후 배포한다.

### 처리와 유효기간

1. 이메일 잠금 안에서 계정·발송 제한을 확인하고, 인증 요청과 암호화한 Outbox 작업을 같은 트랜잭션으로 저장한다.
2. 접수 커밋이 실패하면 worker가 조회할 작업이 없으므로 메일을 보내지 않는다.
3. worker는 짧은 트랜잭션으로 작업을 선점한다. SMTP 호출 중에는 DB 트랜잭션·연결·advisory lock을 유지하지 않는다.
4. SMTP 수락 후 인증의 발송 시각·만료 시각, 발송 성공 이력, Outbox의 SENT 상태를 같은 트랜잭션으로 커밋한다.

- 대기 중 `last_sent_at`은 null이며 코드 확인 대상이 아니다. 필수 만료 컬럼은 접수 시각으로 채워두지만 유효기간을 시작한 상태로 취급하지 않는다.
- 가입용 5분은 SMTP 수락 시점부터 시작한다. 재설정 번호는 필수 외부 설정을 사용하며 개발 서버 v2의 임시값은 300초다. 팀 확정 정책은 아니다.
- 수락 이후 응답 지연·시계 이동으로 남은 시간이 없으면 `expiresIn=0`을 반환하며 성공 기록을 취소하지 않는다.
- SENT는 SMTP 서버 수락을 의미하며 실제 수신함 도착을 보장하지 않는다.

### 프론트 계약 변경: 협의 필요

| 요청 | 응답 | 화면 처리 |
|---|---|---|
| `POST /api/v1/auth/email-verification` | `202`, `{requestId, status: "PENDING", expiresIn: 0}`. `Location`에 조회 주소 | 발송 대기 표시. 인증번호 타이머를 시작하지 않음 |
| `GET /api/v1/auth/email-verification/deliveries/{requestId}` | `200`, `{requestId, status, expiresIn}` | PENDING: 기다림, SENT: 남은 시간으로 타이머 시작, FAILED/CANCELLED: 실패·무효화 안내 |
| 알 수 없는 조회 ID | 본문 없는 `404` | 요청 ID 복구·재요청 안내 방식 협의 |

- 모든 접수·상태 응답에 `Cache-Control: no-store`를 적용한다. 응답에 이메일·코드·해시를 포함하지 않는다.
- 조회 ID는 예측하기 어려운 UUID이며 상태 조회 권한을 가진 값으로 취급한다. URL·로그·분석 도구 공유를 제한한다.
- FAILED는 제한 재시도 또는 대기시간 초과, CANCELLED는 최신 요청 교체·인증 완료·소비·계정 자격 변경에 따른 무효화다.
- 인증 유효기간이 지난 SENT는 `expiresIn=0`이다. 새 인증 요청이 생기면 이전 성공 조회는 CANCELLED로 노출한다.
- 접수 이후 SMTP 오류를 최초 POST의 500 응답으로 돌려줄 수 없다. 상태 조회로 실패를 안내해야 한다.
- 조회 간격·화면 대기 제한·접수 응답 유실 복구·공통 404 오류 형식은 프론트와 협의한다. 현재 접수 API에는 idempotency key를 추가하지 않았다.

### 실패·재시도·동시성

- 내부 상태는 QUEUED / SENDING / RETRY / SENT / FAILED / CANCELLED이며 QUEUED·SENDING·RETRY를 외부 PENDING으로 묶는다.
- `FOR UPDATE SKIP LOCKED`와 lease 토큰으로 다중 worker를 선점한다. 유효한 lease의 작업은 다른 worker가 가져가지 않는다.
- 프로세스 종료나 성공 기록 실패로 SENDING이 남으면 lease 만료 후 같은 작업 ID·코드로 복구한다. 이전 lease 토큰은 새 worker의 상태를 덮어쓰지 못한다.
- SMTP 실패 시 제한된 재시도를 수행한다. 성공 기록 커밋 실패 시 인증의 만료 시각·이력·SENT 갱신을 함께 롤백하고, 먼저 커밋한 발송 작업은 보존한다.
- SMTP 수락 후 응답 유실·DB 오류·lease 만료가 겹치면 같은 메일이 중복 도착할 수 있다. SMTP에는 DB와 같은 트랜잭션이나 정확히 한 번 전달 보장이 없으며, 작업 ID와 같은 코드의 재사용은 중복 작업·서로 다른 번호 혼선을 줄이는 조치다.
- 재시도 상한·최대 대기시간을 넘으면 FAILED로 종료한다. 마지막 시도에서 수락 후 기록 실패가 발생해도 무한 재시도하지 않는다.
- 같은 이메일의 모든 목적을 합쳐 활성 작업은 하나만 허용한다. 대기 중 추가 요청은 AUTH-0004(429)로 차단한다.
- 시간당·일당 제한은 성공 이력에 미성공 접수 작업을 합산한다. FAILED/CANCELLED도 집계 기간 내에는 예약 횟수로 남겨 실패 반복을 통한 우회를 막으며, SENT 작업은 이력으로만 세어 중복 집계하지 않는다.
- 최소 간격은 마지막 성공 시각과 최근 접수 시각을 모두 검사한다. 집계 범위·실패 예약 유지·재요청 안내는 팀 미확정 구현안이다.

### 암호화와 설정

- 검증용 HMAC 해시와 별도로 발송용 6자리 코드를 AES-256-GCM으로 암호화한다. 매번 새 12바이트 nonce를 사용한다.
- key ID·작업 ID·인증 요청 ID·수신 주소·목적·유효기간·코드 해시를 인증 데이터로 묶어 payload 교체·변조를 검출한다.
- 성공·최종 실패·취소·대기시간 초과 시 발송용 암호문을 삭제한다. 코드 원문과 자격증명은 응답·로그·toString에 넣지 않는다.
- `EMAIL_VERIFICATION_OUTBOX_ENCRYPTION_KEY`: 필수. 별도 생성한 32바이트 난수를 Base64로 인코딩해 Secret으로 주입한다. HMAC·SMTP 비밀값과 재사용하지 않는다.
- `EMAIL_VERIFICATION_OUTBOX_KEY_ID`: 기본 `v1`. 대기 작업을 모두 종료하고 암호문이 제거된 뒤 키·ID를 함께 교체한다. 현재 다중 키 복호화는 구현하지 않았으므로 미처리 작업이 있는 상태의 교체는 재시도 실패를 일으킨다.
- `EMAIL_VERIFICATION_OUTBOX_ENABLED`: 기본 true. false 또는 암호화·SMTP 설정 누락이면 새 접수를 AUTH-0006(503)으로 차단한다.
- DB 작업 메타데이터·개인정보 보관기간, 암호화 키 접근권한·교체 절차, 실패 알림·모니터링 기준은 운영 전 팀 협의가 필요하다.

| 설정 (`auth.email-verification.outbox`) | 구현 기본값 | 목적·재검토 조건 |
|---|---|---|
| `max-attempts` | 3 | 최초 시도 포함. 제공자 제한·운영 복구 기준에 맞춰 재검토 |
| `retry-delay-seconds` | 5 | 고정 재시도 간격. 다량 발송 시 backoff·jitter 검토 |
| `lease-seconds` | 120 | worker 장애 복구. SMTP 타임아웃을 늘리면 충분히 길게 함께 변경 |
| `max-queue-age-seconds` | 300 | 발송 시작 전 대기·재시도 한도. 코드 유효기간과 별개 |
| `poll-delay-ms` | 1000 | worker 조회 주기. 부하·화면 대기시간에 맞춰 재검토 |
| `batch-size` | 10 | 한 번의 조회 주기에서 순차 처리할 최대 작업 수 |

위 기본값은 worker 구현을 위한 임시 운영안이며 팀이 확정한 사용자 발송 제한 수치가 아니다.
최소 간격·시간당·일당 최대 횟수·재설정 번호 기간은 필수 외부 설정을 유지한다. 개발 서버 v2의 임시 적용값과 팀 확인 사항은 문서 상단의 2026-10-14 항목을 따른다.

### Outbox 경로의 실제 Gmail 수신 검증 (2026-10-11)

- 비밀번호 재설정 목적의 실제 API 요청에서 HTTP 202, 발송 요청 ID와 Location, PENDING·expiresIn=0을 확인했다.
- 발송 전 인증 요청과 암호화한 Outbox 작업이 커밋되어 있으며, 발송 시각과 성공 이력은 아직 없는 것을 확인했다.
- 별도 worker의 발송 후 상태 조회가 SENT로 전환되고 남은 유효시간을 반환하는 것을 확인했다.
- Gmail 수신함에 도착한 인증번호와 동일 요청의 DB HMAC 해시가 일치했다. 요청 주소의 대소문자가 달라도 회원의 등록 주소로 발송·저장되었다.
- SMTP 수락 시각, 인증의 last_sent_at, 성공 이력의 sent_at이 일치하고 expires_at - last_sent_at이 검증용 300초임을 확인했다.
- 검증한 작업은 시도 1회·발송 성공 이력 1건으로 완료되었으며, SENT 전환 후 발송용 암호문이 삭제된 것을 확인했다.
- 이 결과는 개발용 Gmail의 정상 발송 한 건에 대한 실제 수신 검증이다. 300초는 재설정 검증용 값이며 운영 정책을 확정하지 않는다. 응답 유실·재시도 시 중복 전달 가능성을 제거했다는 의미는 아니다.
- 운영 제공자·공용 발신 계정 검증, 프론트 연동과 AUTH-007 전환은 별도로 남아 있다.
