# Auth·Term 팀 협의 안건

- 확인일: 2026-10-14
- 임시 설정은 팀 확정 정책과 구분하며, 환경변수 정리와 AWS 적용 완료는 별개입니다.

| 우선순위 | 안건 | 협의 담당 |
| --- | --- | --- |
| 1 | 약관 최종 원문·적용 데이터 | 기획·프론트·백엔드 |
| 2 | 도메인·쿠키 연동 환경 | 프론트·인프라·백엔드 |
| 3 | 이메일 인증·재발송·복구 | 기획·프론트·백엔드 |
| 4 | Gmail·Workspace 외 Google 계정의 신규 가입 | 기획·프론트·백엔드 |

## 1. 약관 최종 원문·적용 데이터

### 팀 확인이 필요한 부분

- **가입 화면에 사용할 최종 약관 원문은 무엇인가?**
  → age·service·privacy·marketing 각 항목의 최종본과 승인 담당자 확인.
- **확정 원문을 누가 프론트와 서버에 반영할 것인가?**
  → 프론트 표시 내용·서버 적용 버전·DB 초기 데이터를 같은 기준으로 준비.

### 현재 임의 설정한 내용

- **임시 처리:** 적용 버전 설정과 DB 약관이 누락되거나 일치하지 않으면 가입을 차단합니다(TERM-0004/503).
- **미준비:** 승인 약관 원문·공식 버전·초기 데이터를 임의로 만들지는 않았습니다.

## 2. 도메인·쿠키 연동 환경

### 팀 확인이 필요한 부분

- **실제 연동 테스트와 서비스에 사용할 프론트 주소는 무엇인가?**
  → CORS 허용 주소와 Google 설정에 사용할 주소 확정.
- **Vercel 주소를 유지할 것인가, API와 같은 사이트에서 연동할 것인가?**
  → Vercel 유지 시 타사 쿠키 차단 환경 확인. 필요한 경우 bareum.site 서브도메인 또는 프록시 방식 협의.

### 현재 임의 설정한 내용

- **구현된 임시 설정:** Refresh·CSRF 쿠키는 HttpOnly·Secure·SameSite=None이며, API 호스트에서만 사용합니다.
- **구현된 제한:** CORS는 명시적으로 허용한 Origin에만 쿠키를 포함한 요청을 허용합니다.
- **준비·검증 필요:** 실제 배포 허용 주소 적용과 브라우저의 쿠키 전달·갱신·로그아웃 검증은 남아 있습니다.

## 3. 이메일 인증·재발송·복구

### 팀 확인이 필요한 부분

- **‘인증 유효기간·재발송 - 5분’을 번호 유효기간으로 해석해도 되는가?**
  → 최초·재발송 번호 모두 5분 유효, 재발송 대기는 별도로 60초인 임시안 확인.
- **재설정 번호 5분·이메일당 최근 1시간 5회·24시간 20회 제한으로 시작해도 되는가?**
  → 가입·비밀번호 재설정의 최초 발송과 재발송을 합산하는 기준 확인.
- **인증번호를 몇 번 틀리면 차단하고, 이후 어떻게 다시 인증하게 할 것인가?**
  → 일정 시간 뒤 재시도 허용 또는 별도 복구 경로 선택.
- **인증 완료 증명을 잃으면 어떻게 복구할 것인가?**
  → 이메일을 다시 인증해 기존 증명을 폐기하고 새 증명을 발급할지 결정.
- **비밀번호 재설정 인증 완료 후 새 비밀번호 입력까지 몇 분을 허용할 것인가?**
  → 인증번호 5분과 구분되는 완료 증명 유효기간 결정.

### 현재 임의 설정한 내용

| 항목 | 현재 값 | 구분 |
| --- | --- | --- |
| 회원가입 인증번호 유효기간 | 300초 | 기존 팀 명세 |
| 비밀번호 재설정 인증번호 유효기간 | 300초 | env v2 임시값·팀 확인 필요 |
| 최소 발송 간격 | 60초 | env v2 임시값·팀 확인 필요 |
| 이메일당 최근 1시간 발송 제한 | 5회 | env v2 임시값·팀 확인 필요 |
| 이메일당 최근 24시간 발송 제한 | 20회 | env v2 임시값·팀 확인 필요 |
| 인증 실패 횟수 제한 | 미정 | 값을 설정하지 않음 |
| 비밀번호 재설정 완료 증명 유효기간 | 미정 | 값을 설정하지 않음 |

- 번호 유효기간은 **SMTP 수락 후** 시작합니다. 위 임시값은 환경변수로 지정하며 Java 기본값으로 고정하지 않았습니다. **AWS 적용 완료를 의미하지 않습니다.**
- 발송 제한은 대소문자를 무시한 동일 이메일의 가입·재설정 요청을 합산합니다. 성공 이력과 Outbox 예약을 집계하며, 실패·취소된 작업도 집계 기간 동안 예약으로 남을 수 있습니다. SMTP 자동 재시도는 같은 작업으로 처리합니다.
- **현재 구현:** 재발송·새 최초 요청으로 인증 실패 횟수를 초기화하지 않습니다. 인증 완료 번호의 재확인은 409, 완료 후 재발송은 기존 증명을 보존하며 503으로 차단합니다.
- **미구현:** 실패 제한 도달 후 복구와 완료 증명 분실 후 재발급 경로는 팀 결정 후 구현해야 합니다.

## 4. Gmail·Workspace 외 Google 계정의 신규 가입

### 팀 확인이 필요한 부분

- **Google 인증에는 성공했지만 Gmail·Workspace가 아닌 이메일의 소유권은 어떻게 확인할 것인가?**
  → 우리 서비스의 이메일 인증을 추가할 것인가, 이번 출시에서는 해당 계정의 신규 가입을 제한할 것인가?
- **추가 이메일 인증을 선택한다면 프론트 화면과 가입 요청 형식을 함께 추가할 것인가?**
  → Google 가입 증명과 서비스 이메일 인증 완료 증명을 함께 확인하는 흐름 협의.

### 현재 임의 설정한 내용

- **구현된 임시 제한:** Gmail·검증된 Workspace 계정에만 신규 가입 증명을 발급합니다. 그 외 이메일은 AUTH-0028/403으로 차단합니다.
- Google의 email_verified 값만으로 제3자 이메일의 현재 소유권까지 확인됐다고 처리하지 않습니다.
- **미구현:** 제3자 이메일에 대한 추가 인증·신규 가입 경로는 없습니다. 현재 지원 제한은 팀 확정 정책이 아닙니다.
