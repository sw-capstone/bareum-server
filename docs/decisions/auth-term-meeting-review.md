# Auth·Term 긴급 팀 협의 안건

- 확인일: 2026-10-13
- 범위: 현재 가입·인증 흐름 또는 실제 연동·배포를 막는 미정 사항
- 상태: 아래 선택지는 제안이며 팀 확정 정책이 아니다.

## 회의에서 결정할 네 가지

## 1. 약관 최종 원문과 적용 데이터

**미정인 부분:** 실제 서비스에서 사용할 승인 원문과 그 원문에 대응하는 적용 버전·초기 DB 데이터. 후보·화면 목록만으로 법적 원문이 확정됐다고 처리하지 않는다.

**현재 처리:** 승인 버전 설정과 DB 약관이 일치해야 가입을 허용한다. 누락·불일치 상태에서는 TERM-0004/503으로 차단하며 임의 원문이나 공식 버전을 생성하지 않는다.

**결정·준비 요청:** 약관 원문 최종본과 승인 담당자를 정하고, 프론트 원문·서버 버전 설정·DB를 같은 기준으로 준비한다. 원문 개정·재동의 등 후속 기능은 이번 회의의 필수 결정 대상에 포함하지 않는다.

**영향·재검토 조건:** 승인 전에는 최종 가입 배포 검증을 완료할 수 없다. 원문이 변경되면 적용 데이터의 대응 관계를 재검토한다.

근거: [기술·정책 1.2](https://app.notion.com/p/3e311880adea8077a667c9a8eae3d107), [TERM-001](https://app.notion.com/p/d7711880adea83f9a32e01a207d167e5).

## 2. 실제 도메인·쿠키 연동 환경

**미정인 부분:** 공식 연동 대상 프론트 Origin과, Vercel Preview를 계속 사용할지 API와 같은 사이트의 프론트 도메인을 사용할지.

**현재 선택:** Refresh·CSRF 쿠키는 HttpOnly·Secure·SameSite=None·호스트 전용, 정확한 Origin에만 CORS credentials를 허용한다. 실제 허용 목록 적용과 브라우저 검증은 준비가 필요하다.

**선택지:** 현재 Vercel Origin에서 지원 브라우저의 쿠키 동작을 확인하거나, 프론트를 bareum.site의 별도 서브도메인으로 연결해 같은 사이트에서 연동한다. 도메인 변경은 프론트 배포·DNS·Google Console 설정에 함께 영향을 주므로 백엔드 단독으로 확정하지 않는다.

**결정·준비 요청:** 테스트·서비스 Origin을 지정하고 타사 쿠키가 차단되는 브라우저를 포함해 확인한다. 차단되면 같은 사이트 배포 또는 프록시 방식으로 연동 환경을 조정한다. 서명 키·Client ID·권한 등 환경값 준비는 담당자의 배포 작업으로 처리한다.

**영향·재검토 조건:** 실제 도메인이 없거나 쿠키가 차단되면 갱신·로그아웃·Google 흐름이 동작하지 않는다. 배포 도메인이 바뀔 때 쿠키·CORS·Google 설정을 함께 확인한다.

근거: [AUTH-002](https://app.notion.com/p/57011880adea83868d2801458ac96772), [AUTH-009](https://app.notion.com/p/63711880adea833aadd4811919fa18c9), [연동 안내](../integration/auth-term.md).

## 3. 이메일 재발송·인증 복구

**미정인 부분:** 정책의 ‘인증 유효기간·재발송 - 5분’에서 5분이 재발송 최소 간격도 의미하는지, 인증 실패 제한 도달 또는 완료 증명 응답 분실 후 다시 진행할 방법.

**현재 처리:** 번호 유효기간은 5분이며 최소 발송 간격은 별도 설정으로 받는다. 재발송·새 최초 요청으로 실패 횟수를 초기화하지 않는다. 이미 인증 완료된 번호의 재확인은 409, 완료 후 재발송은 기존 증명을 보존하며 503으로 차단한다. 따라서 완료 증명을 잃거나 실패 제한에 도달한 사용자의 복구 흐름은 완성되지 않았다.

**결정 요청:**

1. 5분을 코드 유효기간에만 적용할지, 재발송 대기에도 적용할지 정한다.
2. 실패 제한 도달 후 일정 시간 뒤 새 인증을 허용할지, 별도의 복구 경로를 둘지 정한다.
3. 완료 증명 분실 시 본인 재인증을 거쳐 기존 증명을 폐기·새 증명을 발급할지, 다른 복구 경로를 둘지 정한다. 프론트의 재시도·타이머·오류 안내와 서버를 함께 맞춘다.

**영향·재검토 조건:** 합의 전에는 실패·응답 유실 상황의 가입 복구를 완료했다고 판단하지 않는다. 허용 조건을 정하면 상태 전이·오류 계약·회귀 사례를 함께 수정한다. SMTP 제공자·발신 계정과 실제 발송 제한값은 인프라·백엔드가 배포 전에 준비하되, 세부 수치 전체를 회의 안건으로 올리지는 않는다.

근거: [기술·정책 1.2](https://app.notion.com/p/3e311880adea8077a667c9a8eae3d107), [AUTH-005](https://app.notion.com/p/4f311880adea82bfa8b301d6b27b2b20), [AUTH-006](https://app.notion.com/p/18311880adea83dea34c81850a8ea665), [AUTH-007](https://app.notion.com/p/90411880adea83bdbdfc816914012c67).

## 4. 제3자 이메일 Google 계정

**미정인 부분:** Google 인증에는 성공했지만 Gmail·Workspace가 아닌 이메일을 사용하는 신규 사용자의 서비스 이메일 소유권 확인 흐름.

**현재 선택:** Gmail·검증된 Workspace만 신규 가입 증명을 발급한다. 다른 이메일은 AUTH-0028/403으로 차단한다. 이 지원 범위는 팀의 확정 정책으로 취급하지 않는다. Google의 email_verified만으로 제3자 이메일의 현재 소유권까지 보장한다고 가정하지 않는다.

**선택지:** 제3자 이메일의 신규 Google 가입에도 서비스 이메일 인증을 추가하거나, 이번 출시에서 지원 계정을 제한한다고 명시한다. 추가 인증을 선택하면 Google 증명과 이메일 완료 증명을 결합하고 프론트 화면·요청 계약을 함께 구현해야 한다.

**영향·재검토 조건:** 현재 AUTH-004의 신규 사용자 흐름에는 이 추가 단계가 없다. Google 연동 공개 전에 지원 범위와 추가 화면을 확정해야 한다. 기존 Google 회원의 sub 식별을 이메일 기반 자동 연결로 바꾸지는 않는다.

근거: [기술·정책 1.3](https://app.notion.com/p/3e311880adea8077a667c9a8eae3d107), [AUTH-004](https://app.notion.com/p/57011880adea8339956d010fe1c43f17), [Google 로그인 기준](google-login-draft.md), [Google 이메일 소유권 검증 안내](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).
