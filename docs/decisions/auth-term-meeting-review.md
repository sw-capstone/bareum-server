# Auth·Term 적용안 및 팀 검토 항목

기존 미정 항목을 개발용 임시 기준으로 구체화했다. 팀 최종 승인·실제 배포와 구분하며 상세 구현·영향·재검토 조건은 [Auth·Term 임시 적용 기준](auth-term-policy-implementation.md)을 따른다.

## 1. 약관
- **구현 기준:** 네 boolean 동의, 필수 동의 검증, DB 약관에 동의 이력을 연결한다. 버전 비교·유효성 검증과 관련 503은 이번 개발에서 제외한다.
- **외부 준비:** 개발 중 임시 원문을 사용할 수 있다. 실제 사용자 가입 적용 전 표시 원문과 DB 기록 기준을 확인한다.
- **팀 검토 질문:** 최종 원문·버전이 준비되었는가? 프론트 표시와 서버 데이터의 반영 담당자는 누구인가?

## 2. 개발 도메인·쿠키
- **임시 적용안:** develop Vercel 미리보기와 api.bareum.site를 연결한다. 정확한 Origin만 허용하고 HttpOnly·Secure·SameSite=None 쿠키를 유지한다.
- **외부 검증:** 배포 설정 적용과 실제 브라우저의 쿠키 전달은 별도로 확인한다.
- **팀 검토 질문:** 이 주소로 연동할 수 있는가? 타사 쿠키 차단 시 같은 사이트 도메인으로 전환할 것인가?

## 3. 이메일 인증·재발송·복구
| 항목 | 개발 적용안 |
| --- | --- |
| 가입 번호·완료 증명 | 기존 300초·600초 유지 |
| 재설정 번호·완료 증명 | 300초·600초 |
| 발송 간격·횟수 | 60초·최근 1시간 5회·24시간 20회 |
| 인증 실패 제한·복구 | 5회 실패 후 15분 대기, 새 번호 접수 시 새 시도 시작 |
| 완료 증명 분실 | 기존 재발송 API로 재인증, 새 접수와 함께 이전 미사용 증명 무효화 |

- **기존 명세 유지:** 재발송 자체는 실패 횟수를 초기화하지 않는다. 제한 시간이 지난 후 새 번호를 요청해야 한다.
- **구현 영향:** 기존 확인·재발송 계약을 사용하며 완료 증명 원문 재조회는 제공하지 않는다. 계정·로그인은 정지하지 않는다.
- **팀 검토 질문:** 실패 5회·15분과 재설정 증명 10분으로 시작해도 되는가? 재인증 시 기존 증명 무효화 안내가 적절한가?

## 4. Google 지원 계정
- **임시 적용안:** Gmail·검증된 Workspace 신규 가입만 허용한다. 제3자 이메일은 AUTH-0028/403으로 안내한다.
- **외부 준비:** 실제 Client ID·승인 Origin 등록 및 Google 계정 연동 검증.
- **팀 검토 질문:** 이번 범위의 지원 제한을 유지할 것인가? 제3자 이메일 추가 인증이 필요하면 별도 화면·계약과 함께 확대할 것인가?
