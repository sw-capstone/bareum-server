# Auth·Term 임시 적용 기준

- 관련 업무: [#54](https://github.com/sw-capstone/bareum-server/issues/54), BRM-45
- 상태: 개발 적용안. 팀의 최종 승인·실제 배포 완료와 구분한다.
- 범위: 약관 적용, 개발 연동 환경, 이메일 인증 복구, Google 신규 가입 지원 범위

이 문서는 기존 미정 항목을 개발 가능한 기준으로 구체화한 것이다. 아래 값과 선택은 팀 확정 정책이 아니며 리뷰에서 변경할 수 있다. 가입 번호 5분·가입 완료 증명 10분, Access 15분·최초 로그인부터 최대 8시간, 네 boolean 약관 동의와 비동기 메일 접수 흐름은 기존 명세·합의를 유지한다.

## Auth1. 약관 동의와 원문

- 프론트가 원문을 표시하고 `agreements.age/service/privacy/marketing`을 보낸다.
- age·service·privacy는 필수, marketing은 선택이다. DB 약관에 연결해 네 응답·버전·시각을 기록한다.
- 별도 버전 환경변수·DB 버전 비교와 원문 확정 대기 503을 제거했다. 개발 중 임시 원문을 사용할 수 있다.
- DB 약관 누락·중복 등 동의 저장이 불가능한 데이터 오류는 TERM-0004/500으로 처리하고 가입 전체를 롤백한다.
- 실제 사용자 가입 전 프론트 원문과 기록할 DB 버전을 함께 확인한다. [근거·영향·재검토 조건](signup-term-consent.md)을 따른다.

## Auth2. 개발 도메인과 쿠키

- 개발 연동안: 프론트 `https://bareum-web-git-develop-numkites-projects.vercel.app`, API `https://api.bareum.site`.
- `LOGIN_ALLOWED_ORIGINS`에는 이 프론트 Origin을 정확히 지정한다. 와일드카드·경로·임의 미리보기 도메인을 허용하지 않는다. 문서 기입은 실제 서버 설정 적용을 의미하지 않는다.
- Refresh·CSRF 쿠키는 HttpOnly·Secure·SameSite=None·호스트 전용·`Path=/api/v1/auth`를 유지한다. 요청은 credentials와 CSRF 계약을 따른다.
- 재검토: 실제 브라우저의 타사 쿠키 차단으로 갱신이 불가능하면 같은 사이트의 프론트 서브도메인 또는 프록시로 전환한다. DNS·인프라를 이 변경에서 수정하지 않는다.

## Auth3. 이메일 인증·재발송·복구

| 항목 | 적용 기준 | 구분 |
| --- | --- | --- |
| 가입 번호 유효기간 | SMTP 수락 후 300초 | 기존 팀 명세 |
| 가입 완료 증명 | 인증 완료 후 600초 | 기존 팀 명세 |
| 재설정 번호 유효기간 | SMTP 수락 후 300초 | env v2 임시안 유지 |
| 재설정 완료 증명 | 인증 완료 후 600초 | 이번 임시 선택 |
| 사용자 발송 제한 | 최소 60초, 최근 1시간 5회·24시간 20회 | env v2 임시안 유지 |
| 인증 실패 제한 | 같은 이메일·목적의 누적 실패 5회 | 이번 임시 선택 |
| 제한 후 재시작 | 5번째 실패부터 900초 후 새 번호 요청 | 이번 임시 선택 |

- ‘재발송 5분’은 재발송 번호도 5분간 유효하다는 의미로 우선 해석한다. 재발송 대기는 별도 60초다.
- 메일 발송 제한은 대소문자를 무시한 이메일의 가입·재설정 요청을 합산한다. 번호 실패 횟수는 이메일·인증 목적별로 누적한다.
- 잘못된 번호는 실패 횟수를 커밋한다. 5번째 실패에서 `attempts_blocked_until`을 DB에 기록하며 이후 확인·최초 발송·재발송으로 제한을 우회하지 못한다. 사용자 계정·기존 로그인은 잠그지 않는다.
- 재발송·새 최초 요청만으로 실패 횟수를 초기화하지 않는다. 제한 종료 후 새 번호 접수가 커밋될 때만 횟수를 0으로 시작한다. 기존 번호는 다시 유효해지지 않는다.
- 완료 증명을 잃거나 만료되면 기존 `POST /api/v1/auth/email-verification/resend`로 새 번호를 요청하고 다시 인증한다. 이메일만으로 완료 증명을 발급·재조회하지 않는다.
- 새 재발송 접수 시 기존 번호·미사용 완료 증명을 함께 무효화한다. 번호 발송·확인에 성공해야 새 완료 증명을 받는다. 이미 소비된 증명의 요청은 재발송으로 복구하지 않는다.
- 접수 자체가 거부되거나 DB 저장이 실패하면 기존 번호·증명·횟수·제한 시각을 보존한다. 접수 후 SMTP 최종 실패는 기존 번호·증명을 되살리지 않으며, 발송 제한 안에서 새 번호를 요청한다.
- 202 접수·상태 조회·PENDING의 `expiresIn=0`·SENT부터 타이머 시작은 유지한다. 제한 중 요청은 `AUTH-0010/429`, 기존 발송 제한은 `AUTH-0004/429`다. 재확인만으로 기존 완료 증명을 재발급하지 않는 409 응답도 유지한다.
- migration은 nullable 제한 종료 시각만 추가한다. 과거 제한 행에 시각이 없으면 마지막 발송 시각(없으면 당시 만료 시각)+900초를 기준으로 복구하며, 거절된 요청으로 대기 시간을 늘리지 않는다.
- 영향: 주소를 아는 사람이 재요청하면 기존 미사용 증명을 무효화할 수 있다. 기존 발송 제한·대기 작업 중복 차단을 유지하고, 접수 응답 유실 시 무조건 POST를 반복하지 않는다.
- 재검토: 인증 성공률·발송 지연·반복 요청·메일 제공자 한도·복구 UX에 따라 횟수와 기간을 조정한다. 아래 수치는 OWASP가 지정한 값이 아니라 초기 적용안이다.

### 후속 인증 배포 설정

```dotenv
EMAIL_VERIFICATION_MAX_VERIFICATION_ATTEMPTS=5
EMAIL_VERIFICATION_ATTEMPT_COOLDOWN_SECONDS=900
EMAIL_VERIFICATION_PASSWORD_RESET_VERIFICATION_TTL_SECONDS=600
LOGIN_ALLOWED_ORIGINS=https://bareum-web-git-develop-numkites-projects.vercel.app
```

코드 기본값은 실패 5회·대기 900초·재설정 증명 600초다. 명시적 잘못된 값은 차단한다. 제한 대기는 1~86400초 범위이며 Parameter Store의 동일 이름으로 선택 주입할 수 있다. 이번 설정은 #18의 메일 발송 전용 env v2를 덮어쓰지 않으며, 후속 인증 기능 배포 시 함께 준비한다. 비밀번호 찾기의 기존 MVP 제외 기준은 유지한다.

## Auth4. Google 신규 가입 지원 범위

- 이번 개발 적용안은 Gmail·검증된 Workspace 계정만 신규 가입시킨다. 기존 Google 회원은 이메일 문자열 대신 검증된 `sub`로 식별한다.
- Google이 현재 이메일 소유권을 보증하지 않는 제3자 이메일 신규 가입은 `AUTH-0028/403`으로 제한하고 지원 범위를 안내한다.
- 제3자 이메일에 `email_verified=true`가 있다는 이유만으로 신규 계정을 생성하지 않는다. 추가 이메일 인증 화면·목적·증명 계약을 이번 변경에 추가하지 않는다.
- 실제 Google Client ID와 Console의 승인 Origin은 리소스 소유자가 준비해야 한다. 가짜 값을 넣어 인증을 통과시키지 않는다.
- 재검토: 제3자 이메일 지원 요구가 생기면 별도 서비스 이메일 인증과 Google 가입 증명의 결합을 설계하고 프론트와 함께 연결한다.

## 검증 및 적용 범위

- 전체 서버 `./gradlew check bootJar --no-daemon`: 688개 테스트 통과, 실패·오류·건너뜀 0개 및 JAR 빌드 성공.
- 복구 통합 테스트 12개: 동시 오입력 제한, 대소문자·최초/재발송 우회 차단, 제한 종료 경계, 새 번호·완료 증명 교체, 기존 증명의 가입 차단, 접수 실패·DB 오류 롤백, 과거 데이터 복구와 증명 소비 후 차단을 확인했다.
- 설정 기본값·재정의·잘못된 대기 시간과 migration·Hibernate 매핑을 검증했다. 메일은 모의 발송이며 실제 브라우저·외부 Google 계정 검증은 포함하지 않았다.
- 배포 설정 모의 검사 22개 중 21개 통과, POSIX 심볼릭 링크 권한 검사 1개는 Linux CI 확인 대상이다. 실제 Parameter Store는 조회·변경하지 않았다.
- 전체 인증 설정 비활성화 상태에서도 #18의 DB·메일 9개와 v2 템플릿을 유지한다. 전체 인증 모드에서 SSM으로 지정한 정책은 대응하는 기존 별칭을 생성 파일에서 제거해 서로 다른 값이 함께 남지 않도록 검증했다.
- #18의 커밋과 env v2는 변경하지 않는다. 선행 인증·배포 정비 PR을 순차 병합한 뒤 이 변경을 최신 기준으로 반영·재검증한다.
- 약관은 개발용 DB 데이터로 연동할 수 있으며 최종 원문·DB 버전 대응은 실제 사용자 적용 전 확인한다. 실제 Google Client ID, AWS 설정 적용과 프론트 연결은 준비·검증 대상이다. 미준비 외부 값을 임의로 생성하거나 배포 완료로 표시하지 않는다.
