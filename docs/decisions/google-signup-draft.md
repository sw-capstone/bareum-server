## 명세 근거와 구현 범위

- [AUTH-011](https://app.notion.com/p/24511880adea833e8870018de01d7df3): 유효한 가입용 증명·필수 약관 확인, 동일 이메일 재확인, 회원·Google 인증수단·약관 이력 저장, 가입 후 자동 로그인.
- [기술·정책](https://app.notion.com/p/3e311880adea8077a667c9a8eae3d107): 2026-10-07 수정본의 계정 정책을 적용한다. Google의 이메일·이름만 사용하고 계정 연결 없이 가입 방식과 관계없이 이메일 중복을 차단한다.
- [백엔드 개발 가이드](https://app.notion.com/p/3e311880adea8071b58be8d1701bd474): 생성 성공은 201, 일반 성공 DTO를 직접 반환하며 오류는 서비스 코드가 포함된 ProblemDetail을 사용한다.
- 약관의 원문은 프론트에 고정하고 `age·service·privacy·marketing`의 동의 여부를 받는다. 기존 가입 약관 검증기로 승인된 ID·버전을 연결하고 동의 여부·응답 시각을 기록한다.
- AUTH-004가 발급한 `gs_` 접두사의 가입용 증명만 받는다. 요청의 이메일·이름·Google 식별자로 프로필을 대체하지 않는다.
- 회원·인증수단·동의 이력·증명 사용·로그인 세션을 하나의 트랜잭션으로 저장한다. 저장에 실패하면 전체를 롤백하여 미사용 증명으로 다시 시도할 수 있다.
- 가입 후 기존 공통 인증을 사용한다. Access Token은 최대 15분, 로그인 세션은 발급부터 최대 8시간이다. 갱신 정보는 HttpOnly·Secure·SameSite=None 쿠키로 전달하며 `/me`·갱신·로그아웃에 연결한다.

## API 계약 초안

`POST /api/v1/auth/signup/google`

- `Content-Type: application/json`
- `GET /api/v1/auth/csrf`에서 받은 쿠키와 `X-CSRF-TOKEN` 헤더를 함께 보낸다. 프론트의 요청은 `credentials: include`를 사용한다.
- 이 경로는 일반 Bearer Token이 필요하지 않다. Authorization 헤더가 있더라도 CSRF 검증은 생략하지 않는다.

```json
{
  "signupToken": "<AUTH-004의 signupToken>",
  "agreements": {
    "age": true,
    "service": true,
    "privacy": true,
    "marketing": false
  }
}
```

성공은 `201 Created`, `Cache-Control: no-store`, `Pragma: no-cache`이며 로그인 응답과 같은 필드를 사용한다.

```json
{
  "accessToken": "<accessToken>",
  "tokenType": "Bearer",
  "expiresIn": 900,
  "sessionExpiresIn": 28800
}
```

갱신 토큰은 본문에 포함하지 않는다. `bareum_refresh` 쿠키는 `/api/v1/auth` 경로에 설정하며 Max-Age는 남은 세션 시간이다. DB에는 목적별 토큰 해시만 저장한다. 응답의 시간은 응답 생성 시 남은 시간을 올림한 초 단위다.

| 실패 상황 | HTTP·코드 | 프론트 처리 기준 |
|---|---|---|
| 필수 필드 누락·가입용 증명 형식 오류 | 400 / COMMON-0002 | errors의 field·message로 입력 안내 |
| 잘못된 JSON 본문 형식 | 400 / COMMON-0003 | 요청 형식 안내 |
| 약관 항목 누락·필수 약관 미동의 | 400 / TERM-0002·0003 | 필요한 약관 동의 안내 |
| 증명 없음·교체됨·만료됨·사용됨 또는 이미 연결된 Google 식별자 | 401 / AUTH-0029 | Google 인증부터 다시 시작 |
| CSRF 실패 | 403 / AUTH-0018 | CSRF 쿠키·헤더와 Origin 설정 확인 |
| 동일 이메일의 LOCAL 계정 | 409 / AUTH-0027 | 이메일 로그인 안내, 자동 연결 금지 |
| 동일 이메일의 다른 가입 계정·DB 이메일 제약 충돌 | 409 / AUTH-0001 | 기존 가입 방식으로 로그인 안내 |
| 약관 구성·승인 버전 불일치 | 503 / TERM-0004 | 가입 준비가 완료될 때까지 중단 |
| DB 저장·커밋 장애 | 503 / AUTH-0030 | 일시적 실패 안내, 증명이 유효하면 재시도 |
| 예상하지 못한 서버 오류 | 500 / COMMON-0001 | 일반적인 실패 안내 |

400 문서는 일반 ProblemDetail과 ValidationProblemDetail을 `anyOf`로 묶은 BadRequestProblemDetail을 참조한다. 오류 응답에 토큰 원문·프로필·SQL·내부 예외 메시지를 포함하지 않는다.

## 동시성·데이터 기준

- 가입 후 서비스 토큰은 JWT로 발급한다. 이전 Access는 재로그인·갱신으로 즉시 폐기하지 않으며, 로그아웃은 해당 family의 Access 전체를 폐기한다. 원문 토큰을 DB에 저장하지 않는다.

- AUTH-004와 같은 Google 식별자 advisory lock을 먼저 획득하고, 가입 증명 행을 다시 조회·잠근 뒤 이메일 잠금을 획득한다. 증명 교체·동시 완료 요청을 직렬화한다.
- 이메일 조회·잠금·DB 제약은 PostgreSQL `upper(email)` 기준이다. 이메일 가입과 Google 가입의 동시 요청도 같은 이메일 잠금을 공유한다.
- Google 식별자의 기존 연결과 이메일 중복은 최종 가입에서 다시 확인한다. 이미 연결된 식별자에 새 계정을 만들거나, 이메일이 같다는 이유로 기존 계정에 연결하지 않는다.
- 증명은 검증 후에도 최종 사용 시점의 만료·미사용 여부를 다시 확인한다. 저장이나 잠금 대기 중 만료되면 가입 전체를 롤백한다.
- 선택 약관을 false로 전달해도 가입 가능하며, 미동의 이력은 동의 시각 없이 응답 시각과 함께 저장한다.
- 사용된 증명은 원래 만료 시각까지 재사용을 차단하는 데 사용되며, AUTH-004의 만료 정리 정책을 따른다.
- 새 테이블·migration·의존성을 추가하지 않고 AUTH-004의 `google_signup_proof`와 기존 회원·약관·세션 구조를 사용한다.

## 쟁점·선택지·영향·재검토 조건

|---|---|---|
| 요청·응답·오류 계약 | 가입용 증명을 JSON이나 별도 헤더로 전달, 신규 성공 DTO 또는 공통 로그인 필드 재사용 | JSON의 signupToken·agreements, 201 및 공통 로그인 필드, AUTH-0029·0030을 사용한다. 프론트 연동 검토 후 확정 |
| 증명 수명과 최신 요청만 유지 | 짧은 가입 대기 시간 또는 재시도 복구를 위한 연장·다중 증명 | AUTH-004의 최대 10분·최신 증명만 유지 기준을 재사용한다. 시간 연장·증명 재발급·성공 응답 유실 복구는 도입하지 않으며 UX 합의 시 함께 재검토 |
| 가입 성공 응답 유실 | 일반 Google 로그인 재시도 또는 가입 완료 요청의 멱등 응답 | 사용된 증명으로는 토큰을 재발급하지 않는다. 계정이 생성됐다면 AUTH-004로 다시 로그인한다. 네트워크 재시도 요구가 정해지면 재검토 |
| 탈퇴 이메일·Google 식별자 재사용 | 이메일을 새 계정에 허용하거나 일정 기간 예약, 기존 식별자 연결을 해제하거나 보존 | #18의 임시 정책대로 DELETED와 탈퇴 시각이 모두 있는 이메일만 중복 대상에서 제외한다. 같은 Google 식별자의 기존 연결은 해제 여부와 관계없이 재가입 증명 발급·완료를 허용하지 않는다. 탈퇴·재가입 정책 확정 시 함께 검토 |
| Google 이메일 소유권·프로필 변경 | Gmail·검증된 Workspace만 신규 가입하거나 별도 이메일 확인, 가입 시 Google 재검증 | AUTH-004에서 허용한 계정의 증명에 보관된 프로필만 사용한다. 별도의 Google 재호출은 하지 않는다. 비 Gmail·Workspace 신규 계정 지원과 증명 대기 중 프로필 변경 처리 요구가 정해지면 재검토 |
| 약관 원문·승인 버전 | 프론트 고정 원문과 서버 승인 버전을 함께 관리하거나 서버 원문 조회 | 기존 고정 약관 계약과 설정을 재사용한다. 승인 버전 설정·DB 약관이 없거나 불일치하면 가입을 차단한다. 임의 운영 약관을 생성하지 않으며 내용 변경 시 양쪽을 함께 수정 |
| 가입 완료 요청 제한 | 발급 단계 제한만 재사용하거나 IP·증명별 완료 요청 제한 추가 | AUTH-004의 발급 제한과 CSRF를 유지한다. 잘못된 증명은 계정을 생성하지 않으며, 별도 완료 요청 제한은 추가하지 않는다. 운영 전 전체 인증 경로의 남용 제한을 검토 |

## 선행 변경과 검증 범위

- #40의 Google 로그인, #18의 이메일 DB 제약·Outbox, #32의 비동기 재발송과 #33의 최신 가입 연동 변경을 반영한다. 선행 PR 병합 전에는 develop 비교에 해당 변경이 포함된다.
- 이메일 인증 설정의 발송·확인 필드를 모두 생성자 바인딩과 final 필드로 유지하고, 기존 인증 확인·가입 테스트를 해당 설정과 Outbox 흐름에 연결한다.
- 실제 Google 계정·프론트 SDK 연결은 Client ID·승인 Origin 및 공개 계약을 맞춘 뒤 별도 검증해야 한다. 테스트의 Google 인증 정보·약관 버전은 검증용이며 운영 설정이 아니다.

## 최종 검증 결과

- `./gradlew check bootJar --no-daemon`: 전체 612개 통과, 실패·오류·건너뜀 0개. Google 가입 완료 관련 49개를 포함하며 JAR 빌드도 성공했다.
- PostgreSQL에서 Flyway 적용·JPA 매핑, 약관·Google 연결·증명 사용·세션의 원자적 저장을 검증했다. 동의·인증수단·세션 저장 실패와 저장 중 증명 만료 시 전체 롤백·재시도를 확인했다.
- 같은 증명의 동시 요청, 같은 이메일·서로 다른 Google 식별자, 이메일·Google 가입 경쟁, Google 로그인의 증명 교체와 가입 완료 경쟁에서 중복 계정·동의 저장을 차단했다.
- 실제 HTTP 요청으로 201·갱신 쿠키·no-store, /me·갱신·로그아웃 연결, 증명 원문 비노출, CSRF·CORS·입력 오류 및 OpenAPI anyOf 참조를 검증했다.
- 기존 이메일 발송·확인·재발송·가입·로그인·토큰 갱신·로그아웃 회귀 테스트가 통과했다. 인증 설정을 테스트에 명시하여 외부 비밀 설정에 의존하지 않도록 했으며, 인증 적용 후에도 GET /health가 공개 상태 점검 응답을 제공함을 검증했다.
- 하네스 정적 검사: 4개 통과, 0개 실패, 해당 없음 3개. 하네스 자체 테스트의 최종 결과는 원격 CI에서 확인한다.
- 실제 Google 계정·프론트 SDK 연동은 미검증이며 Client ID·승인 Origin과 계약 검토가 필요하다.

## 2026-10-12 선행 인증 계약 반영

- 최초·재발송의 202 접수·상태 조회와 가입 흐름을 같은 비동기 계약으로 연결했다. PENDING 확인 거부, SENT 이후 새 번호 확인, 이전 번호 거부와 최종 증명 소비를 검증했다.
- 이메일 회원가입은 인증 메일 수신 주소의 표기를 보존하며, 이메일 중복 비교·잠금·DB 제약은 기존 대소문자 무시 기준을 유지한다. Google 가입은 기존 가입용 증명에 보관된 프로필을 사용한다.
- 문서 HTTP 테스트는 공통 보안 설정과 함께 검증한다. 최신 develop의 CI·이미지 설정을 유지하고 Google 설정 예시는 env/local/.env.example에 연결한다.
- 외부 Google 계정·프론트 SDK 연동을 완료한 결과는 아니다. 실제 Client ID·승인 Origin과 운영 약관 설정·계약 확인 전까지 #41은 Draft로 유지한다.
