## 기준과 범위

- [AUTH-003 명세](https://app.notion.com/p/f5a11880adea82a5ac6f01cd592a59ae)와 [기술·정책 명세](https://app.notion.com/p/3e311880adea8077a667c9a8eae3d107)의 이메일·Google 공통 로그인 종료를 따른다.
- 명세의 인증 Header·응답 형식은 미정이다. [로그인](login-authentication-draft.md)·[토큰 갱신](token-renew-draft.md)의 HttpOnly Refresh 쿠키·CSRF 방식을 재사용한다. 아래 계약과 상세 폐기 기준은 팀 확정 사항이 아닌 구현 초안이다.
- 회원당 한 로그인 구조에서 쿠키가 가리키는 현재 로그인 family를 폐기한다. 장기 로그인 유지·회원 탈퇴·계정 연결은 추가하지 않는다.

- 프론트 develop의 [연동 가정](https://github.com/sw-capstone/bareum-web/blob/develop/docs/backend-integration.md)에서도 로그아웃 성공은 204다. 인증 전달 가정은 이전 내용이므로 최신 쿠키·CSRF 계약과 경로를 소비자 코드에 반영해야 한다.

## 현재 API 계약

`POST /api/v1/auth/logout`

- 요청 본문과 Access Token은 필요하지 않다. `GET /api/v1/auth/csrf`를 `credentials: 'include'`로 호출하여 받은 마스킹된 token을 `X-CSRF-TOKEN` 헤더로 보내고, 로그아웃에도 `credentials: 'include'`를 사용한다.
- Refresh 쿠키는 브라우저가 전달한다. 만료된 Authorization 헤더가 남아 있어도 로그아웃 경로에서는 Bearer 인증을 요구하지 않는다. Authorization·본문의 토큰은 쿠키를 대체하지 않는다.
- 유효한 CSRF 검증 후 성공은 **204 No Content**, 본문 없음, `Cache-Control: no-store`, `Pragma: no-cache`이다. 프론트는 204를 JSON으로 파싱하지 않는다.
- 성공 시 `bareum_refresh`·`XSRF-TOKEN`에 빈 값·Max-Age=0·Path=/api/v1/auth를 설정한다. 발급과 같은 HttpOnly·Secure·SameSite 설정을 사용하고 Domain은 지정하지 않는다.
- 반복 요청, Refresh 쿠키 누락, 형식 오류·알 수 없는 값·만료·기폐기는 204로 처리한다. 유효한 CSRF는 항상 필요하며, Refresh 쿠키 중복은 대상이 모호하므로 401 AUTH-0021로 거부한다.
- CSRF 누락·불일치·중복 헤더는 403 AUTH-0018이고 폐기·쿠키 삭제를 수행하지 않는다. 허용되지 않은 Origin은 CORS 403으로 차단된다.
- DB 조회·저장·커밋 장애는 503 AUTH-0019이다. 폐기를 롤백하고 쿠키 삭제 성공 응답을 보내지 않는다. 요청의 토큰이나 내부 오류는 응답에 노출하지 않는다.
- 프론트는 204 수신 후 메모리 토큰·사용자·문서·분석 상태를 비우고 진행 상태 조회를 중지하여 로그인 화면으로 이동한다. 갱신·로그아웃을 직렬화하고 로그아웃 시작 후 갱신 응답으로 인증 상태를 복구하지 않는다. 다음 쿠키 인증 요청 전에 CSRF를 다시 조회한다.

## 폐기와 동시성

- Refresh JWT 서명·용도·회원·family를 검증하고 회원 → 로그인 세션 순서로 잠근다. 잠금 획득 후 최초 조회한 family와 토큰 소유를 다시 확인한다. 저장된 만료 Refresh도 명시적 종료에는 허용하며 인증·갱신에는 허용하지 않는다. 세션과 같은 family의 등록 Access를 모두 폐기하므로 갱신 전 Access도 더 이상 사용할 수 없다.
- 같은 family에서 이미 갱신에 사용한 Refresh 해시도 로그아웃에 사용할 수 있다. 갱신이 먼저 끝나도 갱신 전 쿠키를 가진 로그아웃 요청이 같은 로그인을 폐기한다. 로그아웃이 먼저 끝나면 갱신은 거부된다.
- 이전 로그인 쿠키나 이전 family의 소비 기록으로 재로그인 후 새 로그인을 폐기하지 않는다. 조회와 잠금 사이 재로그인이 발생해도 family를 재확인한다. 다른 회원의 로그인에도 영향이 없다.
- 이미 폐기한 세션의 폐기 시각은 반복 요청으로 변경하지 않는다. 기존 만료·소비 해시 보존 정책을 재사용하며 신규 migration과 의존성은 추가하지 않는다.
- 회원 상태·가입 방식 검증으로 로그아웃을 막지 않는다. 정지·탈퇴 상태에도 남아 있는 로그인 정보를 폐기하며 Google 회원도 같은 저장 구조를 사용한다.

## 선택지·영향·재검토 조건

| 쟁점 | 임시 구현 기준 | 선택지·영향 | 재검토 조건 |
|---|---|---|---|
| 인증 전달 | Refresh 쿠키 + 명시적 마스킹 CSRF 헤더. Access 인증 생략 | Access 필수 방식은 만료 후 로그아웃을 위해 갱신이 필요. 현재 쿠키 대상만 폐기하며 Bearer만으로 다른 로그인을 폐기하지 않음 | 프론트 로그아웃 연동 계약 확정 전 |
| 성공·반복 | 본문 없는 204, 알 수 없거나 없는 토큰도 쿠키 삭제 | 401 방식은 만료·반복 요청을 오류로 처리해야 함. 현재 로그인 존재 여부를 응답으로 구분하지 않음 | 프론트 오류·재시도 처리 검토 시 |
| 폐기 범위 | 현재 쿠키 family 및 같은 family의 소비 해시 | 모든 기기 로그아웃은 별도 기능. 과거 쿠키가 새 로그인을 폐기하면 의도하지 않은 종료 발생 | 다중 기기·세션 구조 변경 시 |
| 쿠키 제거 | Refresh·CSRF 쿠키 모두 동일 속성으로 삭제 | CSRF 유지안은 재조회가 적지만 로그아웃 후 인증용 쿠키가 남음. 현재 다음 쿠키 인증 전 재조회 필요 | 배포 도메인·쿠키 정책 확정 시 |
| 갱신과 경쟁 | 동일 잠금 순서·family 재검증, 프론트 직렬화 | 서버 폐기가 완료되어도 늦은 갱신 응답이 쿠키를 다시 기록할 수 있으나 폐기된 토큰으로 인증할 수 없음 | 실제 브라우저·다중 탭 연동 검증 시 |
