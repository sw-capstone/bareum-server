# 이메일 인증 재발송 Outbox 전환·협의 초안

> 이메일 인증의 실패 제한·재인증·재설정 완료 증명과 Google 지원 범위는 [2026-10-16 임시 적용 기준](auth-term-policy-implementation.md)을 우선한다. 아래 이전 구현·검증 기록에서 미정 또는 차단으로 표시한 해당 항목은 당시 상태다. 실제 배포·프론트 연결 완료를 의미하지 않는다.

- 상태: 구현 초안 / 공개 계약·미정 정책은 팀 검토 필요
- 확인일: 2026-10-12
- 소유 역할: backend-team, frontend-team
- 관련 작업: AUTH-007, GitHub #27·PR #32, Jira BRM-31

## 기준과 변경 범위

- [AUTH-007](https://app.notion.com/p/90411880adea83bdbdfc816914012c67)의 번호 교체·만료 갱신·실패 횟수 유지·원문 비노출을 유지한다.
- [기술·정책](https://app.notion.com/p/3e311880adea8077a667c9a8eae3d107)의 회원가입 인증번호 5분 기준을 적용한다. 재발송 대기시간·최대 횟수와 인증 완료 후 재발송 허용 여부는 확정하지 않는다.
- #18의 최초 발송 Outbox·암호화·worker·상태 조회를 재사용한다. 별도 발송 worker나 DB migration·의존성을 추가하지 않는다.
- 기존 인증 요청 ID와 인증 실패 횟수는 유지한다. 새 번호와 발송 작업을 함께 커밋하며 SMTP 호출 중 DB 트랜잭션·이메일 잠금을 유지하지 않는다.

## 공개 API 계약 초안

`POST /api/v1/auth/email-verification/resend`

```json
{"email":"user@example.com","purpose":"SIGNUP"}
```

성공은 기존 동기 `200·expiresIn`을 대신해 **202 Accepted**를 반환한다.

```json
{"requestId":"11111111-1111-4111-8111-111111111111","status":"PENDING","expiresIn":0}
```

- `Location: /api/v1/auth/email-verification/deliveries/{requestId}`
- `Cache-Control: no-store`
- 상태 조회는 기존 `GET /api/v1/auth/email-verification/deliveries/{requestId}`를 사용한다.
- requestId는 발송 작업 ID다. 인증 요청의 DB ID는 유지해도 재발송 작업 ID는 새로 생성한다.
- PENDING은 대기·전송·재시도이며 타이머를 시작하지 않는다. SENT는 SMTP 수락·성공 기록 커밋을 의미하며 남은 초로 타이머를 시작한다. 수신함 도착을 보장하는 상태는 아니다.
- FAILED는 최종 실패, CANCELLED는 무효화다. 두 상태의 expiresIn은 0이다. 발송 실패를 접수 성공의 동기 HTTP 500으로 반환하지 않는다.
- 이메일·인증번호·해시·암호문은 접수·조회 응답에 포함하지 않는다.
- 입력 오류의 400 문서는 BadRequestProblemDetail의 anyOf를 참조한다. 계정·제한·설정 오류는 기존 오류 코드와 HTTP 매핑을 유지한다.
- 최신 공통 인증 브랜치와 결합할 때 기존 CSRF·CORS 계약도 적용한다. 본 변경에서 별도 인증 전달 방식을 확정하지 않는다.

## 상태·수신 주소·실패 처리

- 이메일 비교·잠금·제약은 기존 upper(email) 기준을 유지한다. 회원가입은 기존 인증 요청의 주소 표기를 보존하고 비밀번호 재설정은 조회한 회원의 등록 주소로 저장·발송한다.
- 미사용·미인증 최신 요청만 번호를 교체한다. 만료된 코드도 재발송 가능하다. 사용된 요청과 인증 완료 증명은 변경하지 않는다.
- 접수 커밋 시 이전 번호는 무효화한다. 새 번호는 last_sent_at이 없는 대기 상태로 두고 SMTP 수락 후 TTL과 마지막 발송 시각을 설정한다.
- 인증 요청 갱신 후 Outbox 저장에 실패하면 전체를 롤백하여 기존 번호·만료 시각·발송 시각을 복구한다. 접수 후 SMTP 실패 시에는 새 번호를 대기로 유지하고 이전 번호를 되살리지 않는다.
- 최초·재발송은 같은 이메일 잠금과 발송 제한을 사용한다. QUEUED·RETRY·SENDING 작업이 있으면 추가 접수를 차단한다. 성공 이력과 대기·최종 실패 예약을 함께 집계한다.
- worker 재시도는 같은 발송 작업·암호문·번호를 사용한다. 최종 상태에서 암호문을 삭제한다. SMTP 수락 후 DB 오류는 기존 lease 복구로 다시 처리하며 중복 메일 도착 가능성은 남는다.
- 같은 인증 요청의 번호가 교체되면 이전 SENT 작업의 상태 조회는 CANCELLED·expiresIn=0을 반환한다. 이전 발송 ID가 새 번호의 유효시간을 표시하지 않도록 현재 번호 해시도 비교한다.

## 설정·배포 경계

- 기존 EMAIL_VERIFICATION_HASH_SECRET과 Outbox 암호화 키·SMTP·발송 제한 설정을 재사용한다. 테스트에서 사용하는 고정 키를 운영 서버에 적용하지 않는다.
- 추가된 서버 CI의 전체 컨텍스트·이메일 잠금·중복 제약 테스트와 이미지 기동 검증에는 테스트 전용 해시 키를 명시한다. 이미지 헬스 검증은 Outbox worker를 비활성화하고 외부 SMTP를 호출하지 않는다.
- 현재 배포 환경변수 준비 스크립트는 DB 접속 정보만 수집한다. 인증 기능 배포 전 해시 키·Outbox 키·SMTP 및 발송 정책 값을 안전한 설정 공급 경로에 함께 연결해야 한다. 본 변경에서는 운영 Parameter Store를 생성·변경하거나 운영 비밀키를 기본값으로 제공하지 않는다.

## 최종 검증 결과

- `./gradlew check bootJar --no-daemon`: 전체 180개 통과, 실패·오류·건너뜀 0개 및 서버 JAR 빌드 성공.
- 재발송 Controller 21개·HTTP/OpenAPI 1개·서비스 통합 28개 통과. 202·Location·no-store, 400 anyOf, 요청 ID·실패 횟수 유지, 등록 수신 주소와 목적별 TTL을 확인했다.
- 접수 전 DB 오류·상위 트랜잭션 롤백 시 기존 상태 복원, 대기·재시도·전송 중 추가 접수 차단, 실패 예약 집계·최종 실패 후 재요청, 최초·재발송 동시 접수 직렬화를 확인했다.
- SMTP 호출 중 트랜잭션·advisory lock 해제, 수락 후 만료 시작, 같은 번호 재시도·최종 실패·암호문 삭제, 수락 후 성공 기록 DB 오류 복구와 이력 1건 저장을 확인했다.
- 이전 SENT 작업의 상태 조회가 번호 교체 후 CANCELLED·expiresIn=0이 되어 새 번호의 타이머를 표시하지 않는 것을 확인했다.
- SMTP 프로토콜 서버에서 재발송 수신 주소·본문의 번호와 SENT 전환을 확인했다.
- 개발용 Gmail에서 새 재발송 Outbox 경로의 실제 수신 한 건을 확인했다. 202 접수·PENDING·SENT, 수신 번호와 DB 해시, 요청 ID·검증 실패 횟수 유지, 등록 주소 발송·저장, 수락 시각·검증용 TTL·성공 이력 1건·완료 후 암호문 삭제가 일치했다. 검증용 재설정 TTL 300초는 운영 정책이 아니다.
- #41의 인증 확인·가입·공통 로그인·Google 구현과 결합한 검증 조합에서 전체 610개 통과, 실패·오류·건너뜀 0개를 확인했다. 최초 발송→재발송→이전 번호 거부→새 번호 확인→가입·증명 소비 흐름을 검증했다. 이 수치는 PR #32 단독 테스트 180개와 구분한다.
- 선행 가입 브랜치의 흐름 테스트는 재발송 접수 후 worker 완료를 기다리는 비동기 계약으로 갱신해야 한다. Security 의존성을 포함하는 조합의 문서 테스트에는 기존 DocumentationSecurityConfig를 함께 사용한다. 결합 검증은 이 계약을 반영한 조합의 결과이며 선행 PR이 이미 병합되었다는 의미는 아니다.
- 하네스 정적 검사 4개 통과, 실패 0개, 해당 없음 3개. 최신 develop 대비 공식 비밀정보 검사에서 차단·경고 0개를 확인했다.
- 실제 프론트 타이머 연동과 운영 메일 제공자 전달은 미검증이다.
