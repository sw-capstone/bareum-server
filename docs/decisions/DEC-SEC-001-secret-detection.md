# DEC-SEC-001 민감정보 검사에 Gitleaks 도입

- 상태: 결정
- 기록일: 2026-10-03
- 소유 역할: `harness-maintainers`
- 관련 이슈: [#14](https://github.com/sw-capstone/bareum-server/issues/14)

## 결정

- Gitleaks 8.30.1로 파일과 Git 이력을 검사한다.
- 탐지는 Gitleaks에 맡기고, 차단·경고 기준과 안전한 리포트 출력은 프로젝트 코드에서 관리한다.
- 기존 구조·문서 검사와 같은 워크플로 안의 별도 CI 작업으로 실행한다.

## 기존 방식의 문제

기존 `check_secret_patterns()`는 변수명과 대입문 오른쪽의 길이로 판단해 `token = persist(...)` 같은 정상 테스트 코드를 민감정보로 오탐했다. 원인 분석에서 확인한 구조적 문제는 다음 세 가지다.

- **파일 형식을 구분하지 않았다.** env의 `TOKEN=값`과 Java의 메서드 호출·변수 참조를 같은 정규식으로 처리했다.
- **오탐 회귀 테스트가 없었다.** 후보 탐지와 예시값 제외만 확인했고, 정상 메서드 호출·변수 참조의 통과 여부는 검증하지 않았다.
- **실패 위치와 규칙을 알 수 없었다.** 파일명과 일반 오류 메시지만 출력해 어떤 줄과 조건 때문에 실패했는지 파악하기 어려웠다.

여기에 현재 파일만 검사해, 과거·중간 커밋에 추가했다가 삭제한 값도 확인하지 못하는 한계가 있었다.

## 기존 코드 보완 대신 도구를 도입한 이유

- 메서드 호출을 제외하면 이번 오탐은 고칠 수 있지만, 따옴표 없는 설정값·여러 줄 개인키·인증정보별 형식은 별도로 처리해야 한다.
- Git 이력까지 검사하려면 커밋 범위·패치·탐지 위치 처리도 직접 구현해야 한다. 단일 정규식 수정에서 탐지 기능 전반의 유지보수로 범위가 커진다.
- 전용 도구의 공통 규칙과 이력 처리를 활용하고, 팀은 보완 규칙·예외·회귀 테스트·차단 정책에 집중하기로 했다.

도구 도입만으로 세 문제가 모두 해결되는 것은 아니다. 정상 코드 회귀 테스트를 추가하고, 리포트에 규칙 ID·파일·줄 번호·커밋을 남기는 처리를 함께 적용했다.

## Gitleaks를 선택한 이유

- **필수인 Git 이력 검사를 직접 지원한다.** 커밋 범위를 지정해 PR 중간에 삭제된 값도 검사할 수 있다.
- **기본 규칙을 유지하면서 필요한 규칙만 보완할 수 있다.** 일반 비밀번호·DB URL 규칙과 좁은 예외를 추가해 사례로 검증했다.
- **탐지와 차단 판단을 분리할 수 있다.** JSON 결과의 규칙 ID로 프로젝트 코드가 차단 여부를 정한다. 일반 후보를 경고로 남겨 오탐 때문에 CI가 막히는 일을 줄일 수 있다.
- **실행 결과를 추적할 수 있다.** 위치 정보가 있는 결과를 받아 값 자체를 제외한 리포트로 제공한다.

비교한 다른 도구도 사용할 수 있다. TruffleHog는 외부 서비스의 인증정보 유효성 검증이 강점이지만, 이번에는 유효성 검증 없는 형식 기반 검사와 후보 분류를 우선했다. detect-secrets는 baseline·후보 검토 흐름이 있지만, 이번에는 PR 범위와 과거 이력 검사를 우선했다.

Gitleaks의 탐지 성능이 항상 더 좋거나 CI 구성이 단순해서 선택한 것은 아니다. 필요한 검사 범위를 지원하고, 부족한 탐지 규칙과 차단 정책을 분리해 조정할 수 있다는 점을 선택 근거로 삼았다.

## 도입 전 검증

- **조건:** Gitleaks 8.30.1, TruffleHog 3.97.9, detect-secrets 1.5.0을 합성값과 정상 코드로 비교했다. 외부 서비스 유효성 검증은 끄고, 파일 단위 탐지 여부를 확인했다. 실제 계정의 키는 사용하지 않았다.
- **첫 비교 14개:** 탐지 대상 8개·정상 사례 6개에서 Gitleaks는 대상 5개 탐지·오탐 0개, TruffleHog는 3개·0개, detect-secrets는 8개·2개였다. Gitleaks도 일반 비밀번호 3개를 놓쳐 기본 설정만으로는 부족했다.
- **보완 검증 52개:** 첫 묶음을 26개로 확장하고 경계 사례 26개를 추가했다. 경계 사례의 누락 10개·오탐 1개를 확인해 JSON·여러 줄 값·특수문자·해시 예외를 보완했다. 보완 후 두 묶음 모두 기대한 결과와 일치했다.
- **서비스 기준 추가 23개:** DB·OAuth·JWT·DB URL과 정상 사례를 검사했다. URL 규칙 보완 후 21개는 기대와 일치했다. 문서 예시 오탐 1개와 실제 비밀번호가 예외값 `replace-me`일 때의 누락 1개는 남았다. 일반 후보를 경고로 분리한 이유다.
- **이력·출력:** Gitleaks와 TruffleHog는 삭제된 GitHub 합성 토큰을 과거 커밋에서 찾았다. Gitleaks 보완 규칙으로 삭제된 비밀번호와 PR 중간 커밋도 탐지했고, 검사한 합성 DB·OAuth·JWT 값의 출력 마스킹을 확인했다.

이는 한정된 사례·옵션의 결과이며 도구 전체 성능의 순위나 오탐 0건을 뜻하지 않는다. detect-secrets의 현재 파일 스캔과 이력 검사도 동일한 범위의 비교가 아니다. 임시 비교 사례 전체를 영구 회귀 테스트로 저장한 것은 아니다.

## 운영 기준과 영향

- GitHub classic·fine-grained 토큰과 개인키 형식은 차단한다. 실제 사용 가능한 키인지 검증하지는 않는다.
- 일반 비밀번호·키와 미검토 규칙은 경고로 남긴다. 경고에도 실제 민감정보가 있을 수 있어 확인이 필요하다.
- 클라우드가 미정이므로 AWS·GCP는 차단 목록에서 제외한다. 기본 탐지는 경고로 남긴다.
- 테스트 폴더 전체를 제외하지 않고, 명시적인 예시값·해시 패턴만 좁게 제외한다.
- PR은 포함된 커밋, 수동 실행은 받아온 전체 Git 이력을 검사한다. 정기 실행은 두지 않는다.
- 도구·설정·보고서 오류는 실패 처리한다. 로그와 artifact에 탐지값·원문은 남기지 않는다.
- 별도 CI 작업은 외부 실행 파일·Git 이력·결과 처리와 실패 원인을 구조·문서 검사와 구분하기 위한 것이다.

도구 버전과 보완 규칙도 유지보수해야 한다. 새 인증수단·누락·차단 오탐이 발생하면 사례와 정책을 다시 검토한다. Gitleaks의 현재 공식 안내는 신규 기능보다 보안 패치에 집중하므로, 새 기능이나 규칙 업데이트가 필요해지면 유지보수 상태와 대체 도구도 확인한다.
