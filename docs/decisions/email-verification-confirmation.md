# 이메일 인증번호 확인 API 적용 기준

- 날짜: 2026-10-16
- 상태: 구현안·팀 검토 필요
- 소유 역할: 백엔드 인증 담당
- 대상: AUTH-006, GitHub #19

## 쟁점과 선택

인증번호 발송은 Outbox로 접수한 뒤 별도로 완료됩니다. 발송 대기 중인 번호를 확인하거나, 확인 요청이 동시에 들어와 인증 완료 증명을 여러 번 발급하지 않도록 발송 상태와 동일 이메일 잠금을 공유합니다.

- 최신 요청의 `last_sent_at`이 없으면 확인을 거부합니다. SMTP 수락 후 DB에 발송 완료가 반영된 번호만 확인합니다.
- 이메일·목적별 최신 요청을 확인하고, 발송·확인 요청은 동일한 이메일 잠금으로 직렬화합니다.
- 만료·사용 완료·인증 완료 여부를 확인한 뒤 실패 횟수와 코드 해시를 검증합니다.
- 이메일·목적별 요청 조회와 잠금에는 요청 이메일을 사용하고, 코드 해시 검증에는 조회된 `verification.getEmail()`을 사용합니다. 비밀번호 재설정 발송 시 등록된 주소로 생성한 해시와 확인 기준을 일치시키며, DB의 IgnoreCase 비교와 Java 소문자 변환 결과가 다른 유니코드 입력도 같은 저장 주소로 검증합니다.
- 코드 불일치 예외에서도 실패 횟수는 커밋합니다. 다른 저장·커밋 실패는 인증 완료 증명을 포함해 롤백합니다.
- 확인 서비스는 격리 수준을 별도로 지정하지 않고 DB 기본값을 사용합니다. 현재 PostgreSQL 기본값은 READ COMMITTED이며, 동일 이메일 잠금과 코드 불일치 예외의 `noRollbackFor`는 유지합니다. DB 기본 격리 수준을 변경할 때는 잠금 대기 후 최신 요청 조회와 동시성 검증을 함께 재검토합니다.
- 성공하면 32바이트 난수로 만든 완료 증명을 반환하고 SHA-256 해시·완료 시각·증명 만료 시각만 저장합니다. 응답에는 `Cache-Control: no-store`를 적용합니다.
- 이미 완료한 요청의 재확인은 409이며 기존 증명은 유지합니다. 완료만으로 회원 생성·비밀번호 변경·증명 소비는 수행하지 않습니다.

## 공개 API

`POST /api/v1/auth/email-verification/code`

요청:

```json
{
  "email": "user@example.com",
  "purpose": "SIGNUP",
  "code": "012345"
}
```

성공 응답: `200 OK`

```json
{
  "verificationToken": "인증-완료-증명",
  "expiresIn": 600
}
```

| HTTP 상태 | 조건 |
| --- | --- |
| 400 | 입력 오류, 유효하지 않은 요청, 발송 미완료, 번호 만료·불일치 |
| 409 | 이미 인증 완료 |
| 429 | 설정된 확인 실패 횟수 초과 |
| 503 | 확인 실패 제한 또는 해당 목적의 완료 증명 유효기간 설정 누락·오류 |
| 500 | 저장·커밋 실패 등 서버 오류 |

오류 응답은 공통 `ProblemDetail` 형식을 따르며 인증번호·완료 증명 원문을 포함하지 않습니다. `expiresIn`은 인증번호가 아니라 성공 시 새로 발급한 완료 증명의 유효기간입니다.

## 설정과 후속 정책의 구분

| 설정 | 이 변경의 동작 | 선택된 임시 정책과 후속 범위 |
| --- | --- | --- |
| 가입 완료 증명 유효기간 | 기본 600초 | 기존 팀 명세의 10분 유지 |
| `EMAIL_VERIFICATION_MAX_VERIFICATION_ATTEMPTS` | 기본값 없음. 양수 설정 필요 | #54에서 선택한 임시값은 5회. 15분 제한·해제·우회 방지와 함께 후속 반영 |
| `EMAIL_VERIFICATION_PASSWORD_RESET_VERIFICATION_TTL_SECONDS` | 기본값 없음. 재설정 확인에 양수 설정 필요 | #54에서 선택한 임시값은 600초. 후속 정책 변경에서 기본값 반영 |

실패 제한·재설정 증명 기간의 값이 아직 선택되지 않았다는 의미가 아닙니다. 선택된 임시 정책을 구현한 별도 브랜치와 이번 인증 확인 변경의 리뷰 범위를 구분합니다. 이번 변경에는 제한 시간 경과 후 복구, 재발송 API, 완료 증명 분실 후 재인증, 회원가입·재설정의 최종 소비 기능을 포함하지 않습니다.

기존 발송 환경변수·Outbox 설정·배포 템플릿은 변경하지 않습니다. 현재 env v2만 주입한 배포에서는 확인 실패 제한이 없어 새 확인 경로가 503을 반환합니다. 실제 사용자 연동 전 #54의 복구 정책과 필수 설정을 함께 반영해야 하며, 값만 추가해 복구까지 적용됐다고 처리하지 않습니다.

## 영향과 재검토 조건

- 기존 발송·상태 조회 API와 DB 구조는 유지합니다. 새 DB migration은 없습니다.
- 최종 가입·재설정에서는 증명의 이메일·목적·유효기간·미사용 상태를 다시 검증하고, 회원 변경과 증명 소비를 함께 커밋해야 합니다.
- 완료 증명을 잃은 경우의 복구는 #54의 별도 정책을 따릅니다. 이메일 주소만으로 기존 증명 원문을 재조회·재발급하지 않습니다.
- 오입력 제한·완료 증명 기간·복구 계약이 바뀌면 확인·발송·재발송·최종 소비 경로를 함께 검토합니다.

## 검증 결과

- `./gradlew check bootJar --no-daemon`: 전체 175개 테스트 통과, 실패·오류·건너뜀 0개, JAR 빌드 성공.
- 확인 Controller 17개·서비스 통합 12개·OpenAPI/HTTP 1개 및 Outbox 연결 4개로 입력 검증, 실패 횟수 커밋, 동시 요청, 완료 증명 발급과 저장 실패 시 롤백·재시도를 확인했습니다.
- 유니코드 대소문자 처리가 적용되는 PostgreSQL에서 `I`와 점 없는 소문자 `ı`를 포함한 두 주소의 IgnoreCase 일치와 서로 다른 HMAC 입력을 확인했습니다. 등록된 주소로 비밀번호 재설정 발송·Outbox 완료 후 요청 주소로 코드를 확인해, 완료 증명 저장과 실패 횟수 0회를 검증했습니다. API·스키마와 후속 정책의 범위는 변경하지 않았습니다.
- 가입 완료 증명 TTL=0 검사는 정상 실패 허용 횟수 3을 함께 설정한 별도 테스트로 분리했습니다. 설정 바인딩 성공과 두 값을 확인한 뒤 TTL 오류로 거부되는지 검증하므로 실패 횟수 설정 누락이 TTL 검증을 대신 통과시키지 않습니다.
- Outbox 연결은 메일 송신기를 mock으로 검증했습니다. 이 확인 경로의 배포 서버·실제 프론트 연동은 미검증입니다.
