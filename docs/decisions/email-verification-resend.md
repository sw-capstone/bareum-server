# 이메일 인증번호 재발송 API 적용 기준

- 날짜: 2026-10-16
- 상태: 구현안·팀 검토 필요
- 대상: AUTH-007, GitHub #27, Jira BRM-31

## 쟁점과 선택

재발송은 #18의 발송·암호화·Outbox worker·상태 조회를 재사용합니다. 인증 요청 ID와 검증 실패 횟수를 유지한 채 번호 교체와 새 발송 작업을 함께 커밋합니다. 인증번호 확인은 #57의 구현을 사용합니다.

- 이메일·목적별 최신 요청만 교체하고, 최초 발송·재발송·확인은 동일 이메일 잠금으로 직렬화합니다.
- 새 번호 접수 시 기존 번호를 무효화하고 `last_sent_at`을 비웁니다. SMTP 수락과 발송 완료 저장 후 새 번호의 유효기간을 시작합니다.
- 새 번호가 대기 중이면 이전·새 번호 모두 확인할 수 없습니다. 실패 횟수는 재발송으로 초기화하지 않습니다.
- 새 번호가 기존 번호와 같으면 접수를 거부하고 기존 요청을 보존합니다.
- 접수·암호화·저장 실패는 번호 교체와 발송 작업을 함께 롤백합니다. SMTP 재시도에는 같은 번호와 발송 작업을 사용합니다.
- 진행 중인 작업을 교체하지 않습니다. 최종 실패·취소된 작업은 기존 발송 간격과 제한을 충족하면 새 작업으로 재접수할 수 있습니다.
- 이전 발송 ID는 교체된 번호의 타이머를 노출하지 않도록 `CANCELLED`·0초로 조회합니다.
- 회원가입은 기존 요청 주소를 유지하며, 비밀번호 재설정은 회원의 등록 이메일 주소로 저장·발송합니다.

## 공개 API

`POST /api/v1/auth/email-verification/resend`

```json
{"email":"user@example.com","purpose":"SIGNUP"}
```

성공: `202 Accepted`, `Cache-Control: no-store`

```json
{"requestId":"11111111-1111-4111-8111-111111111111","status":"PENDING","expiresIn":0}
```

`Location: /api/v1/auth/email-verification/deliveries/{requestId}`에서 조회합니다. `PENDING` 동안 타이머를 시작하지 않고, `SENT`의 남은 초를 사용합니다. `SENT`는 SMTP 수락과 DB 반영을 뜻하며 수신함 도착을 보장하지 않습니다. `FAILED`·`CANCELLED`는 0초입니다. 접수·조회 응답에는 이메일·인증번호·해시·암호문을 포함하지 않습니다.

| 상태 | 조건 |
| --- | --- |
| 400 | 잘못된 입력, 요청 없음·미발송·사용 완료, 재설정 불가 계정 |
| 404 | 비밀번호 재설정 대상 회원 없음 |
| 409 | 회원가입 이메일이 이미 가입됨 |
| 429 | 최소 발송 간격·시간당·일일 제한 또는 진행 중 작업 |
| 500 | 동일 번호 생성, 접수 저장 실패 등 서버 오류 |
| 503 | 필수 설정 누락 또는 완료 증명 복구 경로 미적용 |

## 설정과 후속 정책

발송 간격·횟수·인증번호 유효기간은 #18의 설정을 그대로 사용하며 새 환경변수·migration·의존성을 추가하지 않습니다. 선택된 임시값은 60초 간격·최근 1시간 5회·24시간 20회이며, 가입·재설정의 최초·재발송을 대소문자를 무시한 동일 이메일 기준으로 합산합니다. 성공 이력과 Outbox 예약을 반영하고 실패·취소 작업도 집계 기간 동안 예약에 남을 수 있습니다.

#54에서 선택한 5회 실패·15분 제한과 완료 증명 분실 복구는 별도 변경입니다. 이번 변경은 완료·부분 완료 증명을 보존하고 재발송을 503으로 차단합니다. 정책이 미정이라는 의미가 아니며, 선택된 복구 구현이 이 범위에 아직 포함되지 않았다는 의미입니다. #57의 확인 실패 제한도 기존 설정 요구를 유지하며 현재 env v2만으로 확인 경로를 활성화하지 않습니다.

## 영향과 재검토 조건

- #57 병합 후 최신 `develop`에서 재발송 변경만 제출합니다. 기존 #32의 선행 변경 전체를 다시 포함하지 않습니다.
- 프론트는 동기 200 응답을 전제로 하지 않고 202 접수·발송 상태 조회 계약을 사용해야 합니다.
- 번호 교체 커밋 후 SMTP가 실패해도 이전 번호는 복원하지 않습니다. 재시도·복구 중 같은 번호의 중복 메일이 도착할 가능성이 있습니다.
- 복구 정책이 반영되면 최초 발송·재발송·확인과 완료 증명 소비 경로를 함께 검증합니다.
- 이 변경의 실제 배포·프론트 연동·실제 제공자 메일 발송은 별도 확인 대상입니다.

## 검증 결과

- `./gradlew check bootJar --no-daemon`: 전체 231개 테스트 통과, 실패·오류·건너뜀 0개, JAR 빌드 성공.
- 재발송 Controller 25개·OpenAPI/HTTP 1개·서비스 통합 28개 및 확인 연결 4개를 통과했습니다.
- PostgreSQL에서 접수 롤백, SMTP 지연·재시도, 동시 요청, 실패 횟수·등록 주소 유지, 이전 발송 타이머 무효화를 확인했습니다.
- 실제 확인 API와 연결해 이전 번호 거부·새 번호 확인·완료 증명 보존·저장 실패 후 기존 번호 확인 및 확인/재발송 동시 요청을 검증했습니다.
- 메일은 mock과 테스트 SMTP 서버로 검증했습니다. 이 분리된 변경의 실제 제공자 메일·배포 서버·프론트 연동은 미검증입니다.
