# 이메일 인증번호 재발송 API 적용 기준

- 날짜: 2026-10-22
- 상태: 구현안·팀 검토 필요
- 대상: AUTH-007, GitHub #27, Jira BRM-31

## 쟁점과 선택

재발송은 #18의 발송·암호화·Outbox worker·상태 조회를 재사용합니다. 인증 요청 ID와 검증 실패 횟수를 유지한 채 번호 교체와 새 발송 작업을 함께 커밋합니다. 인증번호 확인은 #57의 구현을 사용합니다.

- 이메일·목적별 최신 요청만 교체하고, 최초 발송·재발송·확인은 동일 이메일 잠금으로 직렬화합니다.
- 새 번호 접수 시 기존 번호를 무효화하고 `last_sent_at`을 비웁니다. SMTP 수락과 발송 완료 저장 후 새 번호의 유효기간을 시작합니다.
- 새 번호가 대기 중이면 이전·새 번호 모두 확인할 수 없습니다. 실패 횟수는 재발송으로 초기화하지 않습니다.
- 새 번호가 기존 번호와 같으면 접수를 거부하고 기존 요청을 보존합니다.
- 접수·암호화·저장 실패는 번호 교체와 발송 작업을 함께 롤백합니다. SMTP 재시도에는 같은 번호와 발송 작업을 사용합니다.
- 진행 중인 작업을 교체하지 않습니다. 최종 실패·취소된 작업은 기존 발송 간격과 제한을 충족하면 새 작업으로 재접수할 수 있습니다.
- 이전 발송 ID는 교체된 번호의 타이머를 노출하지 않도록 `CANCELLED`·0초로 조회합니다.
- 회원가입은 기존 요청 주소를 유지하며, 비밀번호 재설정은 회원의 등록 이메일 주소로 저장·발송합니다.

## 공개 API

`POST /api/v1/auth/email-verification/resend`

```json
{"email":"user@example.com","purpose":"SIGNUP"}
```

성공: `202 Accepted`, `Cache-Control: no-store`

```json
{"requestId":"11111111-1111-4111-8111-111111111111","status":"PENDING","expiresIn":0}
```

`Location: /api/v1/auth/email-verification/deliveries/{requestId}`에서 조회합니다. `PENDING` 동안 타이머를 시작하지 않고, `SENT`의 남은 초를 사용합니다. `SENT`는 SMTP 수락과 DB 반영을 뜻하며 수신함 도착을 보장하지 않습니다. `FAILED`·`CANCELLED`는 0초입니다. 접수·조회 응답에는 이메일·인증번호·해시·암호문을 포함하지 않습니다.

| 상태 | 조건 |
| --- | --- |
| 400 | 잘못된 입력, 요청 없음·미발송·사용 완료, 재설정 불가 계정 |
| 404 | 비밀번호 재설정 대상 회원 없음 |
| 409 | 회원가입 이메일이 이미 가입됨 |
| 429 | 최소 발송 간격·시간당·일일 제한 또는 진행 중 작업 |
| 500 | 동일 번호 생성, 접수 저장 실패 등 서버 오류 |
| 503 | 필수 설정 누락 또는 완료 증명 복구 경로 미적용 |

## 이메일 인증 진입점과 조회·작업 처리 경계

- 발송·상태 조회·번호 확인·재발송은 `EmailVerificationController`와 `EmailVerificationControllerDocs`에서 함께 관리합니다. 각 서비스는 기존 책임을 유지합니다. API 주소·HTTP 상태·요청/응답·Location·no-store 계약은 유지합니다.
- 일반 조회는 `EmailOutboxQueryRepository`의 JPA/JPQL과 기존 발송 이력 저장소를 사용합니다. 작업 예약 여부·제한 집계·종료 작업 확인·공개 발송 상태 조회를 테이블·컬럼 문자열에서 분리했습니다. Querydsl 의존성은 추가하지 않습니다.
- `EmailOutbox`는 기존 테이블의 조회 전용 매핑입니다. 암호문·키·lease 정보는 읽기 모델에 포함하지 않으며 외부 API에 엔티티를 반환하지 않습니다. 작업 등록·선점·잠금·재시도·완료 기록은 기존 JDBC SQL과 트랜잭션 경계를 유지합니다.
- 상태 조회는 인증 요청·발송 상태·만료 시각·무효 여부를 한 JPA projection 쿼리로 읽습니다. JDBC 변경 뒤 엔티티 캐시에 남은 상태를 사용하거나 여러 조회 결과를 조합하지 않습니다.
- 현재 발송 판단에는 번호 해시 외에 같은 인증 요청의 **다른 발송 ID와 접수 시각**을 함께 확인합니다. 이메일·접수 시각 조건은 기존 Outbox 인덱스를 활용할 수 있도록 유지합니다. 뒤에 접수된 발송이 있으면 과거 SENT는 CANCELLED/0초입니다. A→B→A처럼 번호가 다시 생성돼도 과거 ID가 새 타이머를 반환하지 않습니다.
- 정상 접수는 동일 이메일 잠금과 양수인 최소 발송 간격으로 순서를 보장합니다. 기존 행을 포함해 발송 이력을 조회하므로 새 DB 컬럼·migration 없이 적용합니다. 수동 데이터 변경 등으로 서로 다른 발송의 접수 시각이 같아 순서를 확정할 수 없으면 어느 쪽도 유효한 SENT 타이머로 제공하지 않습니다.
- 예약·성공 이력의 집계 조회는 기존과 같이 동일 이메일 잠금 안에서 실행합니다. 재접수·최종 실패·취소가 발송 한도를 우회하지 않는지 회귀 검증합니다.

## 설정과 후속 정책

재발송의 발송 간격·횟수·인증번호 유효기간은 #18의 설정을 그대로 사용하며 migration·의존성을 추가하지 않습니다. #57에서 이미 추가한 확인 정책 두 값의 문서·배포 주입 누락을 함께 보완합니다. 선택된 임시값은 60초 간격·최근 1시간 5회·24시간 20회이며, 가입·재설정의 최초·재발송을 대소문자를 무시한 동일 이메일 기준으로 합산합니다. 성공 이력과 Outbox 예약을 반영하고 실패·취소 작업도 집계 기간 동안 예약에 남을 수 있습니다.

#54에서 선택한 5회 실패·15분 제한과 완료 증명 분실 복구는 별도 변경입니다. 이번 변경은 완료·부분 완료 증명을 보존하고 재발송을 503으로 차단합니다. 정책이 미정이라는 의미가 아니며, 선택된 복구 구현이 이 범위에 아직 포함되지 않았다는 의미입니다. #57의 확인 실패 제한은 기존 설정 요구를 유지합니다. v2에 누락된 확인 실패 제한과 재설정 완료 증명 기간을 v3에서 추가하며, 이 설정만으로 #54의 제한 해제·증명 복구 구현까지 적용되지는 않습니다.

## 환경변수 v3 적용

[공유 환경변수 v3](https://app.notion.com/p/40111880adea81138633dbfa65f07074)에 따라 로컬 `env.local` 교체 또는 아래 두 항목 추가가 필요합니다. v2의 기존 값·키는 그대로 유지합니다.

| 변수 | 개발 적용값 | 관리 위치·형식 |
| --- | --- | --- |
| `EMAIL_VERIFICATION_MAX_VERIFICATION_ATTEMPTS` | `5` | 서울 SSM `/bareum/dev/server/동일 변수명`, String |
| `EMAIL_VERIFICATION_PASSWORD_RESET_VERIFICATION_TTL_SECONDS` | `600` | 서울 SSM `/bareum/dev/server/동일 변수명`, String, 초 |

두 값은 앞서 선택한 개발 정책을 주입하며 새로운 운영 정책을 확정하지 않습니다. 첫 값은 확인 실패 횟수 한도이고, 두 번째는 인증번호 300초와 별개인 재설정 완료 증명의 유효기간입니다.

- SSM 조회는 기존 9개와 신규 2개를 합쳐 11개입니다. 요청당 최대 10개로 나누고 모든 응답의 이름·누락·중복·형식 검증이 성공해야 `.env.server`를 교체합니다. 실패하면 기존 파일을 보존합니다.
- 신규 두 값은 템플릿에 중복 정의하지 않습니다. 오래된 템플릿 값이 남아 있어도 제거 후 SSM 값으로 한 번만 기록합니다.
- **병합 전에** 두 String 등록 및 EC2 역할의 조회 권한을 확인합니다. 기존 SecureString 네 값의 복호화 권한도 유지합니다. CI의 SSM 모의 테스트는 실제 AWS 등록·권한 확인을 대신하지 않습니다.
- 필수 CI·리뷰 승인·미해결 대화 정리 후 Squash merge합니다. develop 병합은 자동 배포를 시작하므로 SSM 준비를 뒤로 미루지 않습니다.
- 배포 성공 뒤 실제 이미지·설정과 발송→상태 조회→번호 확인의 정상·오류 응답을 확인합니다. `/health`만으로 인증 기능의 적용 완료를 판정하지 않습니다.

## 영향과 재검토 조건

- #57·#59가 병합된 최신 `develop`을 반영하고 재발송 변경만 제출합니다. 기존 #32의 선행 변경 전체를 다시 포함하지 않습니다.
- 프론트는 동기 200 응답을 전제로 하지 않고 202 접수·발송 상태 조회 계약을 사용해야 합니다.
- 번호 교체 커밋 후 SMTP가 실패해도 이전 번호는 복원하지 않습니다. 재시도·복구 중 같은 번호의 중복 메일이 도착할 가능성이 있습니다.
- 복구 정책이 반영되면 최초 발송·재발송·확인과 완료 증명 소비 경로를 함께 검증합니다.
- 이 변경의 실제 배포·프론트 연동·실제 제공자 메일 발송은 별도 확인 대상입니다.

## 기준 문서 충돌과 적용 범위

- 소유 역할: 백엔드. 상태: 병합된 구현 유지, 문서 불일치 검토 필요.
- 쟁점: Notion 개발 가이드에는 Checkstyle 예정·`ddl-auto: update`·배포 Secrets 예정, ERD 개인 메모에는 TTL 캐시 인증이 남아 있습니다. 현재 develop은 Spotless·Flyway/`validate`·SSM 설정 주입·DB Outbox를 사용합니다.
- 선택지: 예전 초안에 맞춰 실행 구조를 변경하거나, 병합된 구현을 유지하고 공유 문서를 정합화합니다. 이 변경은 #18·#57·#59의 구현과 저장소 개발 가이드를 유지합니다. 기존 migration·인증 저장소를 변경하지 않습니다. 배포 주입 경로에는 #57의 누락된 두 설정만 추가합니다.
- 환경변수 v2는 #18의 발송 설정입니다. v3에서 #57의 확인 제한·재설정 완료 증명 설정을 보완하고, #54 복구 정책은 별도로 반영합니다.
- 영향: 새 약관 버전 검사나 503 가입 차단을 추가하지 않습니다. API 명세의 미정 정책을 새로 확정하지 않으며, 이미 선택한 발송 간격·제한과 202/상태 조회 계약을 유지합니다.
- 재검토 조건: 공유 ERD와 적용 DB의 변경, 인증 정책·발송 설정 변경, #54 복구 정책 반영 시 최초 발송·재발송·확인·증명 소비의 계약을 함께 확인합니다.

## 검증 결과

- `./gradlew check bootJar --no-daemon`: Java 25·PostgreSQL 17에서 전체 237개 테스트, 실패·오류·건너뜀 0개, JAR 빌드 성공. Spotless 및 Flyway migration 중복 검사를 포함합니다.
- 회원가입·비밀번호 재설정 각각 A→B→A의 번호 반복을 검증했습니다. 세 번째 발송 대기·완료 후에도 첫 번째와 두 번째 ID는 CANCELLED/0초이고 최신 ID만 해당 목적의 남은 시간을 반환합니다.
- 순서가 모호한 동일 접수 시각에서는 유효한 타이머를 제공하지 않으며, 같은 트랜잭션에서 JDBC가 변경한 상태를 다음 JPA projection 조회가 반영하는지 검증했습니다.
- 통합 컨트롤러의 기존 네 경로, 입력·업무 오류, Location·no-store와 OpenAPI/Scalar 계약을 기존 HTTP 테스트로 검증했습니다.
- 접수 롤백, 확인과 재발송의 동시 요청, SMTP 지연·재시도, 실패 횟수·등록 주소 유지, 예약·발송 이력 집계를 검증했습니다. 이전 번호 거부·새 번호 확인·완료 증명 보존도 유지합니다.
- 배포 생성기의 신규 정책값 주입·누락·형식·숫자 범위·템플릿 중복 제거·후반 배치 실패 검증과 Linux 파일 권한 검사는 배포 보완 커밋의 CI에서 통과했습니다. 리뷰 대응 이후 최신 head의 전체 CI는 별도로 확인합니다.
- 메일은 mock과 테스트 SMTP 서버로 검증했습니다. 실제 AWS 설정·권한, 제공자 메일, 배포 서버·프론트 통합은 별도 확인 대상입니다.
