# 가입 약관 동의 저장 기준

- 대상: AUTH-001, AUTH-011, TERM-001 / #23, #30, #54
- 적용: 이메일·Google 가입의 공통 약관 검증기

## 명세와 쟁점

[화면 세부 기획](https://app.notion.com/p/8db11880adea821da91f01c46e4d3804)은 개발 중 임시 약관 원문을 허용하고, age·service·privacy는 필수, marketing은 선택으로 정한다. [기술·정책 명세](https://app.notion.com/p/3e311880adea8077a667c9a8eae3d107)는 약관별 동의 여부·버전·시각의 기록을 요구한다. [TERM-001](https://app.notion.com/p/d7711880adea83f9a32e01a207d167e5)은 원문을 프론트가 관리하고 서버는 종류·버전·필수 여부를 제공하도록 한다.

현재 개발 범위에서는 AUTH-011의 유효하지 않은 약관 버전 실패 처리를 제외한다. 필수 약관 미동의는 가입 실패로 처리하며, 버전 비교·형식 검사·별도 환경변수와 그에 따른 503은 사용하지 않는다. DB 버전은 동의 이력 연결을 위한 기존 저장 항목으로만 유지한다.

## 적용 기준

- 요청의 `agreements.age/service/privacy/marketing` 네 boolean은 유지한다.
- 서버도 age·service·privacy가 모두 true인지 검증한다. marketing은 true·false 모두 허용하고 응답을 저장한다.
- DB의 네 약관에 종류별로 연결해 동의 여부·버전·응답 시각을 기록한다. 동의한 항목은 동의 시각도 저장한다. 버전은 연결된 term 행으로 추적한다.
- `SIGNUP_TERMS_*_VERSION`, `auth.signup-terms.versions`, 별도 버전 비교와 그에 따른 503 응답을 제거한다. DB에 서로 다른 버전 문자열이 있어도 종류별 한 행이면 정상 기록한다.
- 약관 버전의 유효성·빈 문자열 여부는 가입 조건으로 검사하지 않는다.
- 원문 본문이나 공식 확정 여부는 서버의 가입 조건으로 검사하지 않는다. 개발 중 원문 확정을 기다리지 않는다.
- DB 약관 누락·중복·필수 여부 오류은 동의 이력을 정상 저장할 수 없는 서버 데이터 오류다. `TERM-0004/500`으로 응답하고 회원·동의·증명 소비를 함께 롤백한다. 설정 버전 불일치·원문 미확정에 대한 오류가 아니다.

## 데이터 준비와 영향

서버 term 테이블에는 원문 컬럼이 없다. 기존 스키마의 code·version·is_required 네 항목 데이터가 있어야 member_term의 외래키로 동의 이력을 연결할 수 있다. 원문 작성과 별개로 개발 DB에는 테스트용 네 항목을 준비할 수 있다. 이번 변경은 실제 DB·AWS·프론트 원문을 변경하거나 공식 약관 데이터를 생성하지 않는다.

요청 필드는 바뀌지 않는다. 프론트의 필수 동의 버튼 제어는 유지하며 실제 API 호출에서도 필수 동의를 검증한다. TERM-0004는 503에서 500으로 바뀌므로 기존 가입 준비 중 안내와 구분한다.

## 재검토 조건

실제 사용자 가입에 적용할 때는 표시 원문과 기록할 DB 버전의 대응을 확인한다. 원문 변경·여러 버전 동시 운영·오래 열린 가입 화면 지원이 필요해지면 명시적인 버전 식별 계약과 활성 버전 선택을 함께 검토한다. 현재 boolean 요청만으로 화면에 표시된 버전 자체를 검증한다고 주장하지 않는다.
