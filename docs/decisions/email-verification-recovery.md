# 이메일 인증 복구 보완 (#54)

- 상태: 개발 보완안. 작업 요청에 따라 구현하며 팀 확정 정책 및 배포 완료와 구분한다.
- 기준일: 2026-11-24
- 기준: 기술·정책 명세의 인증번호 5분, 인증 완료 후 가입 가능 시간 10분 및 기존 누적 실패 한도 설정을 유지한다.

## 보완을 위해 추가한 부분

1. 누적 실패 한도(현재 설정 5회)에 도달하면 제한 종료 시각을 저장한다. 임시 대기시간은 900초(15분)이며 팀 확정값이 아니다. 제한 중 최초 발송과 재발송을 거부한다. 제한 종료 후 새 번호 접수가 커밋될 때만 실패 횟수를 초기화한다. 시간 경과만으로 이전 번호를 다시 허용하지 않는다.
2. 인증 완료 증명을 잃거나 가입 기한이 만료되면 기존 재발송 API로 새 번호를 받아 재인증한다. 재발송 접수 시 이전 번호와 미사용 증명을 무효화한다. 이미 가입에 사용한 증명은 복구하지 않는다.
3. 접수 거부나 DB 저장 실패 시 이전 증명·실패 횟수·제한 시각을 보존한다. 접수 후 메일 발송이 최종 실패하면 이전 증명을 복원하지 않으며 기존 발송 제한 내에서 다시 요청한다.

## 영향과 재검토 조건

- API 경로·요청·응답·오류 코드는 유지한다. 제한은 기존 AUTH-0010/429, 발송 한도는 AUTH-0004/429를 사용한다. 부분적으로만 저장된 인증 증명은 데이터 오류로 계속 차단한다.
- 임시 대기시간 900초는 엔티티 내부 상수 한 곳에서 관리한다. 새 환경변수·전용 설정 클래스·환경문서 버전·SSM 등록을 추가하지 않는다. 팀이 대기시간을 확정하면 이 상수를 재검토한다.
- 마이그레이션은 nullable `attempts_blocked_until` 컬럼만 추가한다. 과거 한도 초과 행은 실패 시각이 없으므로 마지막 발송 시각(없으면 기존 만료 시각)+대기시간을 복구 기준으로 삼는다. 거절 요청으로 기준 시각을 연장하지 않는다.
- 이메일 주소를 아는 사람이 재발송을 요청하면 기존 미사용 증명을 무효화할 수 있다. 기존 발송 제한·대기 작업 중복 방지를 유지한다. 최초 발송도 새 인증 흐름을 만들 수 있는 기존 계약을 유지한다.
- 비밀번호 재설정·변경과 Google 계정 연결은 MVP 제외 상태를 유지한다. 공통 인증번호 코드의 PASSWORD_RESET 목적은 기존 동작의 회귀 대상이며 비밀번호 변경 API를 추가하지 않는다.
- 팀이 실패 후 대기시간이나 복구 UX를 확정하거나, 인증 성공률·메일 지연·반복 요청 문제가 발견되면 수치와 처리 기준을 재검토한다.

## 프론트 연결

- 제한 중 AUTH-0010은 잠시 후 새 번호를 요청하도록 안내한다. 서버는 남은 제한 시간을 새 필드로 반환하지 않는다.
- 증명 분실·가입 기한 만료 시 재발송 → PENDING 조회 → SENT의 남은 시간으로 타이머 시작 → 새 번호 확인 → 새 증명으로 가입한다.
- 재발송 접수 후 이전 증명을 가입 요청에 사용하지 않는다. 가입 완료 기한을 단순 연장하거나 이메일만으로 증명을 재발급하지 않는다.

## 검증 결과

- Java 25·격리된 로컬 PostgreSQL 17(ICU)에서 `./gradlew spotlessApply check bootJar --no-daemon` 성공. CI와 같이 인증 한도·재설정 증명 TTL 환경변수 없이 실행했으며 전체 947개 중 945개 통과, 외부 AI 연동 2개 조건부 생략, 실패·오류 0개. 기존 발송·재발송 통합 테스트에는 필요한 실패 한도 5회를 자체 설정에 명시했다.
- 복구 통합 테스트 13개로 동시 오입력, 제한 종료 경계, 최초 발송·대소문자 우회 방지, 증명 분실·만료, 이전 번호·증명 거부, 저장 실패 롤백과 과거 데이터 복구를 확인한다. 기존 확인·재발송 동시성 테스트도 새 복구 동작에 맞춰 검증한다.
- 빈 로컬 DB에 기존 12개와 신규 1개의 Flyway 마이그레이션 적용을 확인했다. 기존 운영 데이터에 대한 실제 적용은 미검증이다.
- 저장소 하네스 검사 5개 통과, 2개 해당 없음. Windows에서 확인하지 못한 자체 테스트는 #76의 Linux 하네스 CI에서 통과했다. 해당 검사 코드는 수정하지 않았다.
- Git 관리 대상과 신규 소스 스냅샷의 비밀정보 검사는 차단 0건이다. 경고 7건은 기존 테스트 예시에서 발생했다. AWS·배포 서버·실제 브라우저 연동은 아직 검증하지 않았다.
