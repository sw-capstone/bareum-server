# 하네스 논의 질문 목록

> 바름 팀이 하네스 운영 방식과 개발 범위를 합의할 때 사용하는 질문지다. 질문에 대한 답과 근거는 회의 후 결정 기록(`docs/decisions/`) 또는 관련 기준 문서에 반영한다.

## 사용 방법

각 질문은 다음 순서로 논의한다.

1. 현재 기획과 최신 하네스 구조에 이미 답이 있는지 확인한다.
2. 지금 결정하지 않으면 개발을 막는지 판단한다.
3. 선택지·영향·재검토 조건을 기록한다.
4. 결정된 내용은 계약, 정책, CI 또는 문서에 반영한다.

## 1. 회의에서 우선 결정할 질문

### 1.1 하네스 담당과 권한

1. 하네스 주 담당자는 몇 명으로 할 것인가? 주 담당자 부재 시 백업 담당자는 누구인가?
2. 하네스 담당자가 관리할 범위는 어디까지인가?
   - `harness/` 검사 코드
   - `.github/workflows/`와 Ruleset
   - 계약·ID 레지스트리
   - `evals/`와 정답셋
   - 기준 데이터 manifest
3. GitHub 저장소 설정·Actions·시크릿·병합 권한을 하네스 담당자에게 어떤 수준으로 부여할 것인가?
4. 담당자 외 팀원은 하네스 규칙 변경 PR을 만들 수 있는가? 가능하다면 최종 승인자는 누구인가?
5. 담당자 교체나 졸업 이후에도 운영할 수 있도록 백업 계정과 인수인계 절차를 어떻게 남길 것인가?

### 1.2 저장소와 CI 경계

6. 제품 저장소를 bareum-web과 bareum-server 두 개로 운영하고, 공통 계약·하네스를 bareum-server 내부에 두는 방식에 동의하는가?
7. 백엔드·AI 담당자가 공통 계약을 확정한 뒤 bareum-web 소비자 검토를 어떤 순서와 기준으로 운영할 것인가?
8. 모든 push와 PR에서 실행할 공통 검사는 어디까지인가?
9. 검사 실패 시 PR을 차단할 검사와 경고만 남길 검사를 어떻게 구분할 것인가?
10. CI가 사용할 Python·Node 등 실행 버전과 의존성 설치 방식은 무엇으로 고정할 것인가?
11. CI에서 사용자 문서 원문이나 비밀정보가 로그·아티팩트에 남지 않도록 어떤 보존 정책을 적용할 것인가?

### 1.3 명세·계약·SSOT

12. `docs/product/planning-final-v1.1.md`의 기획 기준과 `docs/product/service-spec.md`의 구현 요약을 어떤 절차로 동기화할 것인가?
13. Frontend↔Backend, Backend↔AI 사이의 공식 데이터 형식은 어떤 `packages/contracts/` 파일을 기준으로 할 것인가?
14. 계약을 변경할 때 반드시 함께 수정해야 하는 예시 fixture·테스트·문서는 무엇인가?
15. 계약 버전 호환성을 어떤 방식으로 확인할 것인가?
16. 기획문서·결정 기록·계약이 충돌하면 어떤 순서로 조정하고, 결정 결과를 어디에 기록할 것인가?
17. 이슈·PR에 명세 링크, 수용 기준, 관련 ID와 계약 ID를 필수로 넣을 것인가?
18. 명세가 바뀌었지만 코드가 아직 바뀌지 않은 상태를 어떻게 표시할 것인가?

### 1.4 ID와 변경 추적

19. 기능·API·규칙·데이터·평가·하네스 자산에 ID를 부여하는 기준은 현재 규칙으로 충분한가?
20. 새 하네스 검사에 `HAR-*` ID를 언제 발급할 것인가?
21. 폐기된 ID를 재사용하지 않는 원칙과 `replaced_by` 연결을 누가 관리할 것인가?
22. 이슈 번호와 장기 자산 ID를 어떤 방식으로 PR에서 연결할 것인가?
23. ID 레지스트리 변경에 추가 리뷰를 요구할 것인가?

## 2. 개발하면서 검증 후 결정할 질문

### 2.1 검사 범위와 통과 기준

24. 각 영역의 린트·타입·빌드·단위 테스트를 하네스 CI에 언제 연결할 것인가?
25. 계약 인스턴스 검증과 API 호환성 검사는 어떤 기능부터 적용할 것인가?
26. 실패·부분 성공·재시도·멱등성 시나리오를 어떤 기준으로 필수 테스트할 것인가?
27. 검사 결과를 오류, 경고, 미수행, 판단보류 중 어떤 상태로 표시할 것인가?
28. 하네스 통과와 기능 완료를 어떻게 구분해 기록할 것인가?

### 2.2 제품 AI 하네스

29. 규칙으로 처리할 검사와 LLM에 맡길 판정·생성의 경계는 무엇인가?
30. 모든 LLM 호출을 `apps/ai_worker`의 단일 `judge()` 경계로 통일할 것인가?
31. Evidence에 반드시 포함할 원문 위치·법령 조문·기준일 필드는 무엇인가?
32. 증거 부족·검색 실패·모델 시간 초과 시 사용자에게 어떤 판단보류 메시지를 보여 줄 것인가?
33. 원본 문서와 수정 작업 버전, 변경 이벤트를 어떻게 구분해 저장할 것인가?
34. 프롬프트·모델·룰셋·법령 스냅샷·계약·Git SHA를 어디까지 Trace에 기록할 것인가?
35. 입력 형식 우선순위와 표 파싱 실패 표시 단위는 어떤 실험 결과를 보고 정할 것인가?

### 2.3 평가와 품질 주장

36. H0 기준선은 어떤 구현·모델·프롬프트 조합으로 고정할 것인가?
37. 골드셋은 어떤 보고서 유형·오류 유형·난이도를 포함해야 하는가?
38. 정확도 외에 커버리지, 판단보류율, 근거 정확성, 처리시간, 비용, 재시도율 중 무엇을 지표로 삼을 것인가?
39. H0와 H1을 비교할 때 모델·프롬프트·법령 기준일·실행 비용을 어떻게 통제할 것인가?
40. 평가를 실제로 실행하기 전에는 어떤 표현을 금지할 것인가?
41. 정답셋과 평가 결과를 변경할 때 누가 검토하고 어떤 회귀 기준을 적용할 것인가?

### 2.4 운영과 보안

42. CI 로그와 Trace에서 사용자 원문·개인정보·토큰을 어떻게 마스킹할 것인가?
43. 기준 데이터 사용 여부와 스냅샷의 출처·기준일·갱신 주기는 무엇인가?
44. 하네스 검사 실패가 반복될 때 픽스처·회귀 테스트·결정 기록 중 어디로 전환할 것인가?
45. 외부 API나 모델 장애 시 재시도 횟수·백오프·타임아웃·최종 상태는 무엇인가?
46. 검사 보고서와 평가 결과 아티팩트의 보존 기간과 삭제 책임자는 누구인가?

## 3. 회의 결과 기록 양식

| 질문 번호 | 결정 또는 보류 | 선택 근거 | 영향받는 파일·ID | 재검토 조건·기한 | 담당자 |
|---|---|---|---|---|---|
| 예: 1 | 보류 | 팀 역할 논의 후 결정 | `docs/decisions/`, PR 정책 | 첫 기능 PR 전 | 미정 |

보류한 질문도 “미정”으로 끝내지 말고, 결정 시점과 판단에 필요한 증거를 함께 기록한다.

- 저장소 전략: `docs/decisions/DEC-REPO-001-repository-strategy.md`

- 제품 범위·수용 기준: `docs/product/service-spec.md`
- 평가 기준·정답셋: `evals/`
- 팀 사용법: `docs/guide/development-guide.md`
