## 1. 설계 목표와 범위

하네스는 기획·구현·검증·리뷰·실패 학습을 연결하는 통제 구조다. 개발 하네스와 제품 AI 하네스를 분리하되, 제품 실패가 개발 회귀 사례와 결정 기록으로 이어지게 한다.

| 구분 | 목적 | 핵심 자산 |
| --- | --- | --- |
| 개발 하네스 | 명세·계약·ID·코드·테스트·결정 연결 | Issue, PR, CI, 계약, 결정 기록 |
| 제품 AI 하네스 | 입력부터 판정·근거·수정안·결과 노출까지 통제 | 파서, 규칙, RMA, 검색, LLM, CBR, 평가, Trace |

하네스 통과는 최소 병합 조건이지 제품 기능 완성의 증명은 아니다. 제품 기능은 영역별 테스트, 계약 테스트, 평가셋과 사람 검토로 별도 확인한다.

## 2. 저장소 구조와 책임

```text
bareum-server/
├── apps/                     # api, ai_worker, training 실행 단위
├── docs/architecture/backend/ # 세션·업로드·분석 작업·영속성·API 책임 문서
├── docs/architecture/ai/      # 서버 레포 내부 AI 책임 문서
├── packages/contracts/       # 영역 간 계약(계약 확정 시 추가)
├── rules/                    # 제품 규칙
├── prompts/                  # 문서 유형·판정·수정안 프롬프트
├── data/reference/           # 기준 데이터
├── evals/                    # 평가셋·fixture·결과
├── harness/                  # 개발·제품 하네스와 저장소 검사
├── infra/                    # 로컬 실행·배포·관측 설정
├── tests/                    # 계약·통합·불변식 테스트
├── docs/                     # 서비스·아키텍처·결정·하네스 문서
└── scripts/                  # 로컬·CI 공통 명령

bareum-web/                   # 별도 레포: 공개 API 소비와 화면
```

| 영역 | 담당 | 금지 경계 |
| --- | --- | --- |
| bareum-web | 공개 API 계약 소비, 입력·진행·결과 표시 | AI 내부 구현·DB 직접 접근 |
| `apps/api` | 세션·업로드·분석 작업·상태·영속성·API와 내부 AI 오케스트레이션 | 공개 API에서 모델 SDK·내부 프롬프트 직접 노출 |
| `apps/ai_worker` | 서버 레포 내부의 파싱·규칙·검색·RMA·판정·CBR·수정안·Trace 모듈 | 공개 API와 화면 책임 |
| `packages/contracts` | 영역 간 요청·응답·상태·오류·데이터 구조 | 한 영역의 구현 세부사항 |

### 구조 문서와 현재 반영 상태

- 레포 결정과 API·AI 실행 단위 목표는 [`repository-structure.md`](../architecture/repository-structure.md)에 기록한다.
- 백엔드는 기능별 모듈·레이어드 구조를 기본으로 하고 AI 연동은 Port·Adapter 뒤에 둔다. 세부 경계는 [`backend-architecture.md`](../architecture/backend-architecture.md)에 기록한다.
- API와 AI를 하나의 서버 레포에서 관리하되, 실행 시 별도 패키지·이미지·프로세스로 분리할 수 있다. `apps/api`, `apps/ai_worker`, `apps/training`은 각각 API·Worker·학습 실행 단위이며, 공유 계약은 `packages/contracts/`에 둔다.
- 인프라 아키텍처 본문은 아직 작성되지 않았으므로 특정 클라우드·DB·큐·배포 방식을 하네스 조건으로 확정하지 않는다. 현재 반영 범위와 후속 확인 항목은 [`infra-boundaries.md`](../architecture/infra-boundaries.md)에 기록한다.
- 브랜치·커밋·PR·리뷰 규칙은 [`conventions.md`](../architecture/conventions.md)와 [`DEC-GIT-001`](../decisions/DEC-GIT-001-github-flow.md)을 따른다.

## 3. 제품 AI 실행 구조

```text
입력 형식·크기·지원 여부 확인
→ DocumentBlock 생성과 원본 위치 보존
→ 문서 유형·RMA Move/Step 구조화
→ 문서 유형·Move에 따른 규칙 라우팅
→ 결정론 규칙 검사
→ 선택된 기준 데이터 검색, 후속 범위가 승인되면 외부 원문 확장
→ 근거 범위 안의 의미 판정
→ 확정된 이슈에 한해 CBR 사례 검색·수정 방향 보강
→ Schema·근거 실재·근거 도출·수정안 후검사
→ 결과 노출·판단보류·사람 검토
→ 실행·근거·버전·사용자 선택 Trace 기록
```

RMA는 문서 구간의 기능을 구조화하고 검사할 규칙 묶음을 선택한다. 규칙 엔진은 결정론적 기준을 검사하고, RAG는 원문 근거 후보를 제공하며, LLM은 모호한 의미 판단을 보조한다. CBR은 확정된 문제의 수정 방향만 보강하며 판정 전 자동 결정을 수행하지 않는다.

결정론으로 표현할 수 있는 형식·필수 필드·산술·ID·조문 존재·상태 전이는 코드가 담당한다.

## 4. 계약과 ID

계약 정의 → Schema·예시 작성 → 하네스 검사 연결 → 제공자 구현 → 소비자 구현 → 통합 테스트 순서로 변경한다.

공개 API, 내부 작업, 상태·오류, 파싱·규칙·판정 결과의 형식이 확정되면 `packages/contracts/`를 생성해 관리한다. 계약 변경에는 호환성 영향, 예시, 테스트와 웹 소비자 영향을 함께 기록한다.

## 5. 입력과 파싱

1차 지원 입력은 HWPX, DOCX, 텍스트 계층 PDF와 직접 입력이다. 스캔 이미지 문서는 현재 지원 범위에서 제외한다.

`DocumentBlock`은 다음을 보존한다.

- `source_text`와 정규화된 `text`
- 입력 형식에서 제공되는 page, bbox, line, character 위치
- block kind, level, marker, marker type
- `parent_id`, `section_path`
- transformations, confidence, warnings
- `parsed`, `partial`, `unsupported`, `failed` 상태

표 파싱 실패, 스캔 문서, 일부 페이지 실패는 전체 성공으로 표시하지 않는다. 후속 검사를 실행할 수 없으면 해당 축을 `SKIPPED` 또는 `WITHHELD`로 기록한다. `indent_ta`처럼 의미가 불명확한 필드는 의미를 정의한 뒤 사용한다.

직접 입력은 page와 bbox가 없을 수 있으므로 `null`로 기록하고 character 범위를 사용한다. 파일 입력은 가능한 범위에서 page·bbox·line을 보존한다.

## 6. 분석 작업과 상태

분석 작업에는 `analysis_id`, `document_id`, `doc_type`, `contract_version`, `idempotency_key`, `requested_at`, `trace_id`를 연결한다.

큐·워커 제품, 동시성, 타임아웃·재시도 횟수, 취소·재개, 결과 보존·원문 삭제 정책은 결정 기록과 구현 테스트로 관리한다.

| 상태 | 의미 |
| --- | --- |
| `SUCCEEDED` | 필수 단계와 검증 통과 |
| `PARTIAL` | 일부 단계 성공, 다른 단계 실패·미수행 |
| `FAILED` | 시스템·도구 오류로 완료하지 못함 |
| `CANCELLED` | 사용자 또는 시스템 취소 |
| `SKIPPED` | 선행 조건 부족으로 실행하지 않음 |
| `WITHHELD` | 결과 후보가 있으나 검증 조건 부족으로 비노출 |

검색 결과 없음과 검색 실패, 판정 불가와 정상 판정, 형식 통과와 내용 정확성을 혼동하지 않는다.

## 7. RMA와 CBR

RMA 결과에는 문서 유형, block ID와 원본 위치, Move·Step 라벨, 라벨 버전, 신뢰도·상태, 적용 규칙 ID와 라우팅 이유가 포함된다. 문서 유형별 필수 Move와 순서는 별도 기준이 승인된 뒤 적용한다.

Writing Case와 Correction Case를 분리한다.

- Writing Case: 실제 작성 구조를 참고하며 정답이나 우수사례로 간주하지 않음
- Correction Case: 문제·수정 전후·이유·검증 상태가 있고 승인된 사례

CBR은 문서 유형, Rule ID 또는 Move/Step, 메타데이터, 의미 유사도, 승인 상태, 최신성, 개인정보 검토 순으로 검색한다. 임계값 미달이면 사례 없음으로 처리한다. CBR은 위반 개수·위치·등급을 변경하지 않으며, 근거를 대신하지 않는다.

## 8. 제품 출력 계약

분석 실행은 `analysis_id`, `document_id`, `doc_type`, `status`, `started_at`, `completed_at`, `versions`, `coverage`를 가진다. 문서 위치는 `paragraph_id`, `sentence_id`, `table_id`, `move_id`, `source_span`, `parser_status`를 보존한다.

이슈는 `issue_id`, 제품 규칙 `rule_id`, `axis`, 사용자 출력 `severity`, 카탈로그 `rule_severity`, `location`, `evidence[]`, `suggestions[]`, `validation`, `exposed`를 가진다.

근거 실재와 근거 도출 검사를 통과하지 못한 강한 판정은 판단보류 또는 비노출 처리한다. CBR 사례는 근거를 대신하지 않는다.

서비스 화면의 공개 진행은 5단계로 표시하고 내부 단계는 입력 검증, 파싱, RMA·규칙·검색, 판정·수정안, 후검사·결과 제공으로 기록한다. `FAILED`, `SKIPPED`, `WITHHELD`를 구분한다.

## 9. 버전과 Trace

각 실행은 다음을 함께 기록한다.

- 입력 해시와 문서 유형
- 파서·RMA 라벨 버전
- 모델·프롬프트 해시
- 규칙 카탈로그 버전
- 선택된 기준 데이터 snapshot과 외부 검색 출처. 기준 데이터를 사용하지 않으면 snapshot은 `null`
- 계약 버전과 Git SHA
- 검색 후보·판정·검증·재시도
- CBR 사례 ID·승인 상태·적용 여부
- 최종 상태·노출 여부·사람 개입
- 처리시간·토큰·비용

입력 위치 → 추출 블록 → RMA 라벨·라우팅 → 규칙·검색 자료 → 모델 판단 → 검증 → CBR 사례 → 수정안 후검사 → 사용자 노출·채택·기각의 연결을 보존한다. 사용자 원문과 비밀정보는 그대로 저장하지 않고 해시 또는 비식별 참조를 사용한다.

## 10. 데이터셋과 평가

데이터셋 제안의 등급은 다음과 같다.

- A: 결정론적 변형 가능
- B: 여러 유효 답이 있어 생성과 사람 검토 필요
- C: 외부 사실이 필요해 실제 사례 수집 필요

등급은 위반 사례를 만드는 방법이며 데이터셋 `split`과는 다르다.

문서별 위반 사례는 `evals/datasets/`에서 관리한다. 문서 1개를 인스턴스 1개로 저장하고, 문서 정보·위반 라벨·검사 이력·원문 위치를 보존한다.

| 구분 | 필드와 기준 |
| --- | --- |
| 문서 정보 | 문서 식별자, 분할, 출처, 라벨 생성 방식, 문서 유형, 검사 이력 |
| 위반 라벨 | 규칙 ID, 원문 위치, 수정안과 검수 상태 |
| 합성 정보 | 변형 함수, 위치, 변경 전후 문자열과 생성 버전 |

`split`은 `cbr`, `dev`, `test`만 사용하고 dataset manifest의 배정 결과를 따른다. 같은 `base_doc_id`에서 파생된 원본과 합성본을 서로 다른 split에 넣지 않는다.

`labels`가 비어 있더라도 `checked_rules`에 있는 규칙만 “확인했지만 위반 없음”으로 해석한다. 두 목록에 모두 없는 규칙은 정상이 아니라 미확인이다. `rule`이 만든 라벨은 동일 검출기의 평가 정답으로 쓰지 않고, `synthetic`은 합성 결과 검증 후, `model`은 사람 검수 후에만 평가 정답으로 쓴다.

데이터셋의 문서 유형과 공개 입력 유형의 매핑도 담당자가 계약을 확정할 때 함께 정의한다.

Writing Case, Correction Case, 최종 평가셋을 분리한다. 사용자 채택이나 LLM 생성만으로 정답을 확정하지 않는다.

RMA와 CBR은 같은 평가셋에서 적용 전후를 비교한다.

- RMA 적용 전·후 구조 판정과 검사 라우팅
- CBR 적용 전·후 수정안 품질
- Writing Case와 Correction Case의 역할 분리
- 사례 없음 처리와 부적합 사례 주입률
- 파싱 위치 복원, 근거 적절성, 판단보류 적절성

서비스 목표 `N-01`, `N-02`, `N-04`, `N-06`, `N-07`, `N-09`를 운영·안전 평가와 연결한다. 데이터셋 수량과 점수 산식은 승인 전까지 품질 게이트로 사용하지 않는다.

## 11. 단계별 구현과 완료 조건

### 0단계 — 실행 가능 상태 정의

- 책임 디렉터리와 기준 문서
- 계약·ID 레지스트리
- 규칙·프롬프트·기준 데이터·평가 확장 지점
- 최소 저장소 검사와 자체 테스트

### 1단계 — 계약과 얇은 전체 흐름

- 입력·분석 상태·결과·오류 계약
- 가짜 파서·가짜 분석 결과를 이용한 영역 연결
- 부분 실패·판단보류·계약 호환성 테스트

### 2단계 — 결정론 기능과 데이터

- 확정 입력 형식의 파서와 위치 왕복 테스트
- 문서 유형별 규칙
- 선택된 기준 데이터 manifest·체크섬·완전성 검사
- 규칙 결과 재현성

### 3단계 — 검색·판정·수정안

- 근거 검색과 Recall@5 평가
- 구조화 판정과 Schema 게이트
- 근거 실재·근거 도출·수정안 후검사
- 부분 실패·호출 상한·판단보류

### 4단계 — 평가와 운영

- 승인된 H0와 변경안 비교
- RMA·CBR·검색·프롬프트 실험
- 품질·보류·처리시간·비용 추세
- 실패 사례 회귀셋 승격
- 필요성이 확인된 자동화·배포 정책

## 12. CI와 품질 게이트

현재 CI는 필수 경로, JSON 문법, Schema 헤더, 등록된 Schema·예시 쌍, ID 레지스트리, Markdown 링크, 비밀정보 패턴, GitHub 관리 기획 문서의 필수 표식, 백엔드 책임 문서의 검증 연결 상태와 하네스 자체 테스트를 검사한다. Schema 헤더는 저장소 전체의 `*.schema.json`을 대상으로 하고, Schema·예시 쌍과 ID 레지스트리는 정책 또는 대상 파일이 있을 때 실행한다. JSON 리포트는 각 검사를 통과·실패·적용 없음·비활성으로 구분한다.

Git Flow의 `main`·`develop`과 PR 제목·브랜치·커밋·리뷰 우선순위는 저장소 운영 규칙으로 관리한다. 하네스는 이 규칙을 문서·링크·필수 CI의 존재로 확인하지만 브랜치를 자동 생성하거나 코드·PR을 대신 수정하지 않는다.

기능 구현과 함께 추가할 게이트는 다음과 같다.

| 변경 영역 | 추가할 검사 |
| --- | --- |
| `packages/contracts/` | 전체 Schema 메타검증과 제공자·소비자 호환성 |
| `rules/` | 규칙 ID·필드·상태·카탈로그 버전 |
| `apps/ai_worker/`의 파서 영역 | DocumentBlock·fixture·원본 위치 왕복 |
| `apps/ai_worker/` | 파서·규칙·검색·판정·CBR 단위 테스트 |
| `data/reference/` | 기준 데이터 manifest·체크섬·원문 실재 |
| `evals/` | 인스턴스 Schema·split 누수·지표 계산 |
| `bareum-web/` | 공개 계약이 확정된 후 소비자 검증과 `npm run check` |
| `apps/api/` | 포맷·린트·타입·단위·통합·빌드 |

실행 단위에 코드를 추가할 때는 `apps/api`, `apps/ai_worker`, `apps/training`의 책임·링크·CI를 함께 갱신한다. `packages/contracts/`를 기준으로 웹 소비자 검증을 연결한다.

### 백엔드 반영 기준

9/9 회의 안건에서 정리된 백엔드 범위는 세션·업로드·분석 작업·상태·영속성·공개 API다. 하네스는 다음 순서로 이를 검증한다.

1. 공개 API 요청·응답·오류 계약을 먼저 확인한다.
2. 작업 생성의 멱등성, 상태 전이, 재시도·취소와 부분 실패·판단보류를 계약 테스트로 확인한다.
3. 원문·결과·Trace의 저장·조회·삭제 경계와 로그의 개인정보 비노출을 확인한다.
4. 실제 백엔드 코드와 실행 명령이 추가되면 포맷·린트·타입·단위·API·DB/마이그레이션 검사를 CI에 연결한다.

현재 명령이 없는 영역은 미수행으로 기록하며, 문서 검사만 통과했다고 백엔드 기능이 구현되었다고 판단하지 않는다. AI는 별도 제품 저장소가 아니라 백엔드 내부 모듈로 연결한다.

미실행 검사를 통과로 표시하지 않는다. 현재 하네스 리포트는 검사별 실행 상태와 실패한 검사 ID, 심각도, 경로, 이유를 기록한다. 기능별 게이트를 추가할 때 재현 명령과 다음 행동도 해당 리포트에 연결한다.

## 13. 위험 변경과 승인

| 변경 | 필요한 증거 |
| --- | --- |
| 공개 API·결과 Schema | 호환성 결과와 소비자 영향 |
| 규칙 ID·위험도·판정 조건 | 회귀셋과 오탐 영향 |
| 프롬프트·모델·검색 설정 | 동일 데이터셋의 품질·시간·비용 비교 |
| 기준 데이터·외부 원문 | 출처·기준일·체크섬·완전성 |
| CBR 검색·사례 승인 정책 | 사례 적합률·부적합 주입률·개인정보 검토 |
| CI·권한·비밀정보 | 최소 권한·실패·복구 절차 |

LLM 심판, 검색 모듈, CBR, 장기 메모리 같은 실험 부품은 feature flag, fallback, 불변식 테스트를 갖춘 뒤 활성화한다. 근거 없는 법적 판정을 확정 결과로 노출하지 않는 조건은 항상 유지한다.

## 14. 팀 운영과 장기 유지

경로별 리뷰 자동 지정은 사용하지 않는다. 검토 책임은 PR 담당자 지정과 최소 1명의 승인, CI 통과로 관리한다.

- 하네스 담당: `harness/`, `scripts/`, CI, ID 레지스트리와 공통 게이트
- 기능 담당: 기능 기대 결과, 단위 테스트와 실패 사례
- 영역 담당: frontend·backend·AI 실행 명령과 테스트
- 전문 검토자: 고위험 법령 적용, Correction Case 승인, 평가 정답 확정

결정이 필요한 항목은 임의로 확정하지 않고 결정 기록과 `pending` 상태로 관리한다.

하네스도 버전·평가·회귀 검사의 대상이다. 오래된 규칙·문서·사례·Trace를 정기적으로 점검하고 Specification Drift와 끊어진 참조를 CI에서 탐지한다.
